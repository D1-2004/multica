# 多场域配置：租户、三级场域与 Context Builder（2026-10-01）

分支 `feat/context-capabilities`（CR 36347416）。这份文档讲清楚这一轮做了什么、为什么这么做、怎么上线和回滚。接口字段和完整契约以
`docs/context-capabilities.md` 为准，连接器和 OAuth 细节以 `docs/internal-mcp-connectors.md` 为准。

## 1. 目标和边界

**要解决的问题**

- 同一个智能体会被很多企业使用。每个企业在这个智能体下建一个「租户」，绑定的员工不同，但智能体本身的全局 MCP 和 Skill 对所有企业通用。
- 智能体在不同场合要带不同的上下文：整个企业通用的规则、某个群的约定、某个人自己的账号和偏好。
- 这些上下文要能在网页上按「企业 → 群聊 / 个人」逐级配置，并且在执行任务时真正生效。

**这一轮做到的**

1. 租户：手动创建，必须填钉钉 OrgId；智能体当前绑定的钉钉组织自动算作一个租户。
2. 三级场域：企业级（租户）、群聊级、个人级（单聊就是这个人）。网页左侧是树：租户 → 群聊 / 个人。
3. Context Builder：每一级由「组件」拼成——Prompt、MCP（连接器 + 自定义 MCP 服务器）、连接应用、Skill；有一个「生效预览」显示最终合并结果。
4. 运行时生效：任务启动时按「全局 → 企业 → 群聊 → 个人」合并后注入。
5. 手机配置页按 企业 / 本会话 / 我的 三级展示；个人配置继续靠聊天里发的配置链接领取。
6. Coordinator：别人问「你有哪些能力」时，回答末尾附上配置链接。
7. OAuth 回调：预发发起的连接回调到正式域名，由正式转回预发；正式发起的直接回调正式。不需要任何环境变量。

**不在这一轮**

- 一个智能体同时绑定多个钉钉组织的身份（派单、A2A 身份仍是一个组织）。现在其他企业的租户只在任务记录了该企业的派单 OrgId 时生效。
- 部门等更细的企业级子层（数据模型留了扩展余地，界面没做）。
- 用登录身份直接识别「我是谁」（unionId → staffId）。个人配置仍靠链接领取。
- DSH 插件的场域化配置。

## 2. 数据模型

所有表都没有外键，删除靠应用代码在同一个事务里清理；每张表都带 `workspace_id`、`agent_id`、`org_id`。

| 表 | 作用 | 迁移 |
| --- | --- | --- |
| `agent_tenant` | 租户：一个智能体在一个企业（OrgId）下的名字 | 9420 建表，9421 唯一索引 (agent_id, org_id) |
| `context_prompt_component` | Prompt 组件：某一级上的一段命名提示词（名称、顺序、正文） | 9422 建表，9423 唯一索引 (agent_id, scope_type, org_id, scope_key, name) |
| `context_capability_binding` | 某一级开启了哪个连接器 / Skill | 9424 增加 `org` 级 |
| `context_connector_credential` | 某一级自己的账号或令牌（加密存储） | 9425 增加 `org` 级 |
| `context_scope_mcp_config` | 某一级的自定义 MCP 服务器 | 9426 增加 `org` 级 |
| `connector_oauth_state` | 进行中的 OAuth 连接 | 9427 增加 `org` 级 |
| —— | 把旧的「场域提示词」复制成名为「场域提示词」的 Prompt 组件（可重复执行） | 9428 |

**三级怎么定位**

| 级别 | scope_type | scope_key | 说明 |
| --- | --- | --- | --- |
| 企业级 | `org` | OrgId | 对这个企业里所有群聊和个人生效 |
| 群聊级 | `scene` | 群的 openConversationId | 只对这个群生效 |
| 个人级 | `person` | 员工 staffId | 这个人自己的配置；他的单聊直接用这一份 |

智能体当前钉钉身份的组织不需要建行就算租户（来源标为 `identity`），可以改名，不能删除。删除其他租户时，只删这个租户的企业级配置，群聊和个人的数据保留，树里会显示为「未建租户的企业」，可以重新创建。

## 3. Context Builder：组件和覆盖规则

每一级的配置由四类组件组成：

| 组件 | 来源 | 合并方式 |
| --- | --- | --- |
| Prompt | 每一级可以加多条，每条有名称和顺序 | **同名下级覆盖上级**（个人 > 群聊 > 企业），其余按顺序拼接 |
| 自定义 MCP 服务器 | 每一级可以写自己的服务器配置 | **同名下级覆盖上级** |
| 连接器 / 连接应用 | 通用能力（智能体绑定的）一直生效；「公开给场域」的由各级自己开启 | 通用能力 + 各级开启的，取并集 |
| Skill | 通用能力（智能体绑定的）一直生效；「公开给场域」的由各级自己开启 | 通用能力 + 各级开启的，取并集 |

规则和 DSH 的 context 一致：离任务越近的那一级说了算，同名就替换。合并只有一份代码（`contextcap.MergeContext`），网页上的「生效预览」和运行时用的是同一份，所以预览看到的就是任务拿到的。

**通用能力和公开给场域（第 7 条，2026-10-01 第二版）**

- 智能体页上已绑定的 Skill、已授予的连接器和连接应用叫「通用能力」，默认对所有租户、所有场域生效，没有逐项开关。场域和个人只在它上面叠加：自己的 Prompt、自己的 MCP 服务器，以及给通用连接器换成自己的账号（群聊、企业、个人都可以，不用先公开）。
- 原来的「允许群聊 / 个人开启」改名「公开给场域」，只管智能体**没有绑定**的条目：公开后，群聊、单聊和个人可以自己开启。默认什么都不公开。Skill 页的公开列表不再列已绑定的 Skill；Aone FaaS 连接器和连接应用一旦是通用能力，就不再显示这个开关。
- 连接应用：「添加」直接设为通用能力（以前是公开给场域）；打开通用能力不再要求先连共享账号，没有共享账号时只有连了自己账号的群聊和个人能用。
- 场域页（Context Builder 和手机配置页）把通用连接器列出来，标「通用能力」，不带开关，只能连账号。
- 安全取舍：群聊级的账号会被群里所有人的任务使用，所以只有智能体管理员能给群聊的通用连接器换账号；拿到本群配置链接的成员只能查看（见下面「谁能改」）。

**谁能改**（严格方案，2026-10-01 第二轮起）

| 级别 | 智能体管理员（工作区所有者 / 管理员、智能体所有者） | 本人 | 其他人（拿到配置链接的成员） |
| --- | --- | --- | --- |
| 企业级 | 全部能改 | — | 看不到 |
| 群聊级 | 全部能改（开关、账号、Prompt、MCP） | — | 只能查看 |
| 个人级（单聊就是这个人） | 只能查看（手机配置页和网页 Context Builder 都一样） | 全部能改 | — |

- 这张表只写在服务端一个函数里：`contextCapScopeRights`（`server/internal/handler/context_capabilities.go`），返回「开关 / 连账号 / 改 Prompt / 改 MCP」四项权限。手机配置页和网页 Context Builder 的每个写接口、OAuth 连接的发起和回调都用它判断，产品以后调整规则只改这一处。
- 接口把这四项作为 `rights` 返回给页面，页面按它决定哪些按钮可用；不满足时服务端返回 403（个人级是 `person_only`，企业级和群聊级是 `manager_only`）。
- 管理员仍然可以在网页上「撤销访问」个人级的配置页授权，这不算修改个人配置。

## 3.1 第二轮：配置页（第 1–6 条）

冬翔提的六条需求，这一轮的服务端部分：

1. **标题**改成「QwenTag配置」（前端）。
2. **页面绑定场域**：从链接打开的页面只显示链接对应的那一个场域，群聊链接只看到这个群，单聊和个人链接只看到这个人，不能切换（前端；服务端照旧按授权和场域解析，单聊的 key 落到这个人身上）。
3. **管理员看到企业配置**：企业级只返回给智能体管理员，其他人拿到的 `org` 是空的，写入一律 403。
4. **「公开能力」Tab**：「通用能力」和「企业公开能力」直接用已有的 `global` 和 `offers` 字段，服务端没有新接口。
5. **按 Tab 路由**：前端用 URL 参数选 Tab，服务端无改动。
6. **能配置的更多**：
   - 手机配置页可以新增、编辑、删除、启停 Prompt 和 MCP 服务器。新增两个接口：`PUT /api/context-capabilities/agents/{agentId}/prompts`（整份替换，校验和网页一样）和 `PUT /api/context-capabilities/agents/{agentId}/mcp-config`。
   - 手机上只能加**远程** MCP 服务器：必须有 http / https 的 `url`，只允许 `type`、`headers`、`disabled` 这几项；带 `command`、`args`、`env`、`cwd` 的本地命令一律拒绝（400 `invalid_mcp_config`），保留名 `multica`、`c<16 位十六进制>` 也拒绝。本地命令服务器仍只能在网页上加。
   - **启停**：Prompt 多了 `enabled` 开关（迁移 9431 加列，默认开）；MCP 服务器在自己的配置里写 `"disabled": true`。关掉的条目还保存着，但不参加合并：既不生效，也不会覆盖上一级的同名条目。运行时和「生效预览」是同一份合并代码，所以两边一致；`disabled` 这个键不会传给运行环境。
   - 各级的接口返回里多了 `rights`、`prompts`、`mcp_config`（工作区开了密钥脱敏时不返回内容，只给 `mcp_config_redacted: true`）。
   - 权限按上面「谁能改」的严格方案：群聊配置链接的持有人只能看，不能再给全群换账号；管理员对个人级只能看。

**上线注意**

- 9431 只加一列，可重复执行，旧版本不读它。
- 滚动发布期间旧副本还按旧规则：会应用已关掉的 Prompt 和 MCP 服务器，群聊链接持有人仍能开关和连账号，管理员仍能改个人级，新的两个手机接口返回 404 或 405。发布完成后这些都会消失；如果测试时在窗口期关过什么，发布后再确认一遍。
- 开了密钥脱敏的工作区，手机页看不到已存的 MCP 服务器，保存时会整份替换。

## 4. 运行时怎么生效

任务启动（认领）时：

1. **定位**：企业 = 任务记录的派单 OrgId，没有就用智能体当前钉钉组织；群聊 = 群消息的会话；个人 = 单一发起人的 staffId。
2. **租户门槛**：企业必须是这个智能体的租户，否则场域配置全部不生效。A2A 任务、手动重跑、不是钉钉派来的任务也不带场域配置。
3. **合并注入**：
   - Prompt：在智能体指令末尾追加一段「## 场域上下文」。
   - 自定义 MCP 服务器：合并进本次任务的 MCP 配置；如果和 Runner 已挂载的服务器重名，让给 Runner，并记一条日志。运行环境不支持 MCP（如没有 mcp 能力的 Pi 沙箱）时跳过并记日志，不会取消任务。
   - 连接器和 Skill：加上各级开启的。
4. **账号凭证优先级**：个人 > 群聊 > 企业 > 工作区共享账号，通用能力和公开给场域的连接器都按这个顺序。连接器的每一次调用都会重新按这个顺序取凭证，所以中途关掉、换账号会立即生效。
5. **日志**：每次认领写一行 `context builder: claim context`，只记数量和组件名，不记提示词正文、服务器配置和凭证。

没有场域配置的任务，认领结果和以前逐字节相同（有测试保证）。

## 5. OAuth 回调转发

问题：预发域名的回调在钉钉和部分服务里回不来，GitHub App 也只配了正式回调。

做法（域名按部署自己判断；唯一用到的配置是预发和正式本来就共用的 A2A 转发注册密钥 `MULTICA_A2A_FORWARD_REGISTRATION_SECRET`）：

- 预发的域名是正式域名加 `pre-` 前缀（`pre-fde-workbench.dingtalk.com` ↔ `fde-workbench.dingtalk.com`）。
- **预发发起**的连接：发给服务方的回调地址用正式域名；state 里带上预发的地址。
- **只转预发登记过的连接**（和 A2A 转发注册同一套做法：预发签名、正式验证）：预发发起连接时，先用共享密钥签名，把这次连接（state 的哈希、预发域名、工作区、智能体、连接器、范围、过期时间）登记到正式；正式只接受自己的 `pre-` 域名，存进 Redis，到 state 过期为止。登记失败预发就不发起这次连接。
- **正式**收到回调后，只有 state 指向「pre- + 自己的域名」且预发登记过这次连接时才 302 转回预发，登记用一次就作废；没登记、用过、过期或指向别处的一律报错页，并记日志（带工作区、智能体、连接器）。不会被利用成任意跳转（还要求正式域名是某个注册域名下的子域名）。
- 预发完成换 token、存账号；浏览器绑定 cookie 一直在预发域名上，转发不影响防冒用。
- **正式或本地发起**的连接直接用自己的回调。
- OAuth 应用在授权页显示的名字：预发 `QwenTagPre`，其他 `QwenTag`（GitHub 显示的是 GitHub App 自己的名字）。改名或换回调地址后，每个连接器第一次连接会重新注册一次客户端，旧客户端保留，已连接的账号照常续期。

## 6. Coordinator 配置链接

- 只在开了 Coordinator 的智能体上生效，其他智能体完全不变。
- 当 Coordinator 的回复里有「我能做什么」这类能力说明时，服务端在这段回答末尾加一行配置链接：群聊里是场域链接（30 分钟，可多次用），单聊里是个人链接（15 分钟，一次性，领取后也拿到这个单聊）。
- 链接由服务端生成，模型看不到；Coordinator 自己的日志和 trace、会话记录（两条入站路径都是）、渠道引擎存档的计划、Issue 描述、之后读回的钉钉历史里都只写 `[configuration link]`。执行器 `create_context_config_link` 生成的链接留在这次任务自己的记录里（任务消息、最终输出），因为送达、失败兜底回复和收尾的「已送达」比对都要读回原文。
- 任何异常（没有可信的会话信息、超时、出错）都不加链接，回复保持模型原文。
- 策略：义务 COORD.F04 + 对照用例 `f04_capability_answer_config_link`，`scripts/check-coordinator-policy.py` 通过（结构检查）。

## 8. 灰度和回滚

**灰度**

- 先上预发。场域配置只对「有配置」的智能体产生影响：没有建任何 Prompt、开关、自定义 MCP 的智能体，运行时什么都不变。
- 预发验证顺序：网页上给测试智能体建租户 → 群聊 / 个人各加一条 Prompt 和一个开关 → 在测试群发消息 → 用 Langfuse 看本次任务的指令里有没有「## 场域上下文」、认领日志里组件名对不对 → 问 Coordinator「你有哪些能力」看是否带链接 → 手机打开链接配置「我的」。
- 正式发布另走流程（须莫分身代发，需冬翔授权）。正式发布时要同时完成：GitHub App「QwenTagPre」加回调地址 `https://fde-workbench.dingtalk.com/api/github/authorize`。在正式带上转发之前，预发上发起的 OAuth 连接会停在正式的报错页（令牌方式的连接不受影响）。
- 连接器一直打开，没有开关。正式的旧版本读 Diamond `features.internal_mcp_connectors`，在正式默认关闭；正式发布前把它设成 `true`，滚动期间落到旧副本的连接器调用才不会 404。新版本不读这个键。
- 发布前检查「只存不生效」时期存下的配置：预发和正式各跑一次 `SELECT workspace_id, agent_id, org_id, scene_key FROM agent_scene_config WHERE scene_kind = 'dm' AND BTRIM(prompt) <> '';` 和 `SELECT workspace_id, agent_id, scope_type, org_id, scope_key FROM context_scope_mcp_config WHERE scope_type IN ('person', 'scene');`。这一版开始，单聊提示词变成这个人的组件，个人级自定义 MCP（可能带令牌）也会在这个人单独触发的群聊任务里生效。有结果就先告知配置人或清掉。

**回滚**

- 代码回滚：重新部署上一个版本即可。迁移都是新增表、放宽约束、复制数据和加索引，旧版本照常运行：旧代码不读新表，也不会用企业级（`org`）的凭证和开关，旧的场域提示词也还在原表里。例外是显示：旧版本的连接应用页面会把企业级凭证列成 `scope_type: "org"` 的使用行。
- 旧副本删除工作区时不清理这一版新增的十张表（没有外键），滚动期间或回滚后会留下孤儿行。发布完成后对每张表跑一次 `DELETE FROM <表> WHERE workspace_id NOT IN (SELECT id FROM workspace);`（表名见 `docs/context-capabilities.md` §7）。
- 不需要执行 down 迁移；如果一定要清掉，down 文件齐全，但会丢失新建的租户和 Prompt 组件。
- 某个场域的配置出问题：在网页上关掉对应开关或删掉 Prompt，下一次任务立即不再带上。

## 9. 已知限制

- 智能体身份仍只绑定一个钉钉组织。其他企业的租户，只有任务记录了该企业的派单 OrgId 才生效；没有钉钉身份的智能体，群聊和个人配置仍可用，但树里看不到它们（空 OrgId 无法出现在租户路径里）。
- 个人配置在这个人单独触发的群聊任务里也会生效，所以不要把自己的令牌写进个人级的自定义 MCP 服务器配置里，应该用连接器的账号。
- 个人链接领取后没有校验「领取人就是这个 staffId 的本人」（unionId ↔ staffId），属于后续工作。
- 连接应用页面里的「使用情况」还没有区分企业级。
- 每次连接器调用会多几次数据库查询来重新取凭证。
- Coordinator 配置链接只做了服务端测试和结构检查，还没有真实模型回放和预发端到端验证。
- 执行器生成的链接在这次任务自己的送达副本里（最终输出、评论触发任务的回复评论）保留原文，因为钉钉回复就从这里发出；能看到对应 Issue 的成员能看到。个人链接一次性、15 分钟，被抢占可以撤销。
- 改名身份租户会存一行 `agent_tenant`；智能体换绑到别的钉钉组织后，旧组织留作普通租户，要在场域树里手动删除。
- 删除租户和同时写入的企业级配置没有加锁，写入可能晚于删除留下企业级行，重建租户时会带回来。
- 动态注册的 OAuth 客户端过期或被删除后不会自动重新注册；客户端已失效的凭证、被撤销的 PAT 不会自动删除，仍按 个人 > 群聊 > 企业 > 工作区 优先，调用时提示重新连接，不会退到下一层。
- 配置链接不做清理，过期行只占空间（查询已有索引）。
- 跨组织群里外部成员若被派单带上本组织以外的 staffId，可能和本组织的人撞号（见 `docs/context-capabilities.md` §8 最后一条）。
- 网页 Context Builder 的自定义 MCP 保存接口还接受保留名（`multica`、`c<16 位十六进制>`），只在运行时和预览里被剔除；手机配置页的接口已经拒绝保留名。

## 10. 审查结论和修复清单

合并 develop 之后做了五路审查（权限、凭证与 OAuth、运行时与 Coordinator、数据与迁移、前端），没有 High。处理结果：

- 配置链接泄漏（中）：渠道引擎的 Coordinator 会话记录与存档计划、Issue 描述、读回的钉钉历史都改为占位符（含百分号编码形式）。任务消息一度也替换了，复审发现失败兜底回复会把占位符发给用户、收尾会误判没送达而重复回复，已撤回；执行器自己的记录保留链接（§9）。新增管理员撤销接口 `DELETE .../context/{scopeType}/{scopeKey}/grants` 和场域树里的「配置页访问 → 撤销访问」，被抢占的个人范围可以收回。
- OAuth 刷新持锁等待（中）：行锁改为 `FOR UPDATE NOWAIT`，同进程合并刷新（singleflight），拿不到锁时令牌仍有效就直接用、已失效就在事务外轮询；刷新失败后 30 秒内不再重试。
- 首轮影子请求与认领请求不一致（中）：是否附链接的判断移到 `prepareFirstRound`，两边共用。
- 连接器没有关闭开关（中）：不改。按要求不加开关，出问题时回滚代码或在网页上关掉对应授权。
- 9428 与「只存不生效」配置（中）：补了发布前检查 SQL；9428 同时修正为只认未过期授权、没记 OrgId 的任务算身份组织、同一人取最近一条，并补了迁移测试。
- 低优先级已修：人员列表和计数不再算过期授权；重试任务按第一次派单时间判断是否早于换绑；9429/9430 索引；删除技能时按工作区清理开关；前端 `connected` 参数校验、凭证可选连接器不再报缺凭证、配置页重新登录后保留连接结果；文档更正旧副本对企业级行的显示。
- 其余低优先级列在 §9。
