## P0-2：当前事项与自然续接

- Task 是独立工作聚合，不以 Issue 的状态、评论或 ID 作为 Direct 执行的前置条件。沿用 GawkBot 的目标定义、追加式任务记录、输入关联和 Work Object Compiler；Issue 仅作为 Coordinator 派发适配器的可选映射。
- PostgreSQL 保存 Task、目标版本、追加输入、Run、等待项、效果幂等与投递回执，并以事务和版本校验保证恢复。Redis 复用现有通知、租约和并发协调；通知丢失、重复或缓存清空不能丢任务、重复执行或复活已停止工作。不能引入第二套任务事实来源或执行器。
- 给出经过权限验证的相关 Task 目标、实际状态、已完成内容、下一步和等待输入；不要要求用户手写 UUID。
- Loop 判断进度询问、补充、纠正、继续、闲聊或新事项；单一可信候选可续接，多候选才澄清。
- 同一事项延续同一 Task/目标版本历史，复用既有运行与队列控制，不新建重复任务。新增条件不能让旧结果冒充当前目标的完成。
- 真 IM：开始一项任务 → 进度怎样 → 改成表格 → 辛苦了。核真实 Task/Run 和回复，不因闲聊取消工作。
- 持久层和恢复测试覆盖：两个并发纠正的版本冲突、同源事件重投、提交后进程崩溃、缓存/通知丢失、停止 ACK 前禁止恢复、旧版本结果禁止发出。Direct 测试必须在没有对应 Issue 的情况下完成完整生命周期；Issue 适配器另测原有 Coordinator 行为。

### 与固定 GawkBot 源的取舍

- `task_addressing.go` 用线程、来源任务或显式任务引用定位；“最近一个就是当前任务”不是它已有的安全保证。这里的 `t1` 等引用是 Host 按当前调用者筛选的有限候选，不能从历史文字、被 @ 的人或任意模型 UUID 推导授权。
- `task_ledger.go` 从已观测动作和执行结果组装下一轮工作背景，不调用总结模型。保留这个机制；PG 账本不照搬它最多持久化 20 条的裁剪，只限制每轮注入量。
- `notification_context.go` 的人工纠正优先和 `ContextUsed` 继续通过现有 Compiler 使用；构造提示词不得清除停止门、消费待处理输入或猜测默认私聊目的地。
- 已有 `Store.ObserveIssueRun` 内的 Issue/queue 关系查询应迁到 `service.EmployeeIssueBackend`，核心 Task 只接收经过适配器验证的执行事实。可空的旧 Issue 映射不要求为此重做存储迁移。
- 第一段实现先开放成功终态的明确续接；failed/cancelled 在真实进程退出证明接好前继续拒绝重启。运行中纠正、停止及恢复另做完整闭环，不把队列取消字段或 Redis TTL 当成停止证明。
- Redis empty-claim cache 的失效通知丢失可能受现有 TTL 延迟影响；测试应核实上界，不能宣称通知丢失后立即恢复。

## P0-3：跨场域收集与停止

- 复用 Coordinator 的 assoc/outreach/waiting_on；Task 归属发起场域，其他场域仅提供该 Task 的授权输入，记忆与权限仍隔离。
