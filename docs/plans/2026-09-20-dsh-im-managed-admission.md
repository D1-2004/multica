# DSH 标准会话与消息统一接入 Multica（以 IM 为首个验收）

状态：2026-09-20 已获准在 CR 36224658 实施并部署预发；本文件的验收条目在实际验证前不代表通过。替代本次全量插件化重构目标。

## 目标与范围

在现有重启/配置/角色/reset 修复 CR 基础上，将原生网页已有的会话/消息接入规则下沉为 DSH 宿主侧标准插件服务。原生网页、IM 和其他插件调用受支持的标准会话 API 时，都自然经过同一入口，完整复用 Multica 的现有任务链路。IM 是首个真实验收对象，不是唯一适配对象。

用户补充明确：不能把修改 IM 的 HarnessClient 作为最终方案，也不能要求每个新插件接入 Multica 专用 SDK。此前关于逐客户端适配/兼容包的选项取消；若正式宿主服务扩展无法透明覆盖调用，必须明确报告缺失接口，不擅自改成第三方插件私有兼容分支。

保留当前 DSH 版本、源码补丁、任务调度、任务上下文绑定、原生日志、定时任务及子 Agent 实现。本次不追求官方包零补丁，不新增全局输入批次模型，不改造所有第三方插件，不升级 DSH。

现有 CR 曾确认编号为 36224658，应用工作树为 `dsh-native-restart-guard-20260920`，Runtime 为 `dsh-managed-restart-runtime-20260918`。实施前核对 CR 当前状态与基线，沿用这一需求的 CR；本文没有查询最新发布状态或提交发布。

## 已确认基础

- `handler.submitDSHNativePrompt` 已组合原生会话登记、发送、回执与平台展示事件。
- `TaskService.RegisterDSHNativeChatSession` 已维护原生 Session 与平台 ChatSession 映射，但当前限定浏览器的人类调用身份。
- `TaskService.SendDSHNativeChatMessage` 最终复用 `sendDirectChatMessage`，已有用户消息、任务、请求绑定的事务和重复请求处理。
- 执行端已有 `task.bind -> prompt -> follow -> release`；角色、MCP、Skills 与工具身份沿用该路径。
- `dsh_native_routing.go` 已按持久化绑定查找 Session owner；网页能跨实例读取，但 IM 进程内调用不会自动获得同样的路由。
- IM 前序调查显示其公共客户端使用宿主 API 创建 Session、发送 prompt 并读取 history。微信错误 MF-484E1E79 表现为接收成功、空原生会话、无对应平台任务。宿主无任务上下文时拒绝 prompt，与此现象一致。

上述基础意味着可以做有限扩展，不需要重建调度器。浏览器与插件共享业务服务，但不能把后台插件伪装成已登录的浏览器。

## 目标链路

```text
原生网页 / IM / 其他插件（保持调用标准接口）
  -> DSH 标准会话服务：HTTP、Remote、兼容 API、进程内调用
  -> Multica 会话接入插件（统一身份、登记、路由、消息接入）
       写入 -> Multica 现有 ChatSession / ChatMessage / Task 接入
               -> 现有 claim、上下文绑定、原生 prompt 执行
       读取 -> 正确 Session owner 的原生状态 / page / follow
  -> 按 DSH 标准协议返回对应请求的状态、结果和事件
  -> 原生网页展示 / IM 原有发送器回复 / 其他插件消费
```

通过 DSH 正式 Profile/Bundle 组合插件，提供或组合公开的会话服务，保持服务 key、Remote 契约、请求字段及事件语义。必须验证同一服务实例覆盖浏览器 HTTP/Remote、官方兼容载体和进程内 `sessionController` 等调用，不能只注册另一个 HTTP URL。不得修改第三方客户端、官方类原型或私有字段，不靠加载顺序抢同名接口。

2026-09-20 已从锁定的 DSH `0.1.6-alpha.1` 代码确认公开服务替换机制：`SessionController` 为公开导出的类，Profile 可以替换 `session-controller` 配置行；Gateway 根据服务 key 动态获取实例再分发，Remote 初始化器可在子类上保留方法标记。因此标准会话主链路不需要新增官方源码补丁即可提供受管实现。此结论不等于 IM 所有路径均经过该服务，也不等于完成预发验收。

## 最小改动的接口边界

外部继续使用 DSH 已有的 `sessionController` 和 `session.*` Remote 契约，不新建让网页或 IM 改用的 Multica 专用会话 API。Profile 中只挂载一个会话服务提供者，受管实现继承公开控制器，对需要平台接入的方法做组合，其余复用原生实现；同步返回方法不能擅自改成 Promise。保留官方 Typert schema 和客户端贡献，不能只替换类而丢掉协议注册。

内部复用现有会话登记、任务事务和 owner 路由，按以下职责收口，不重做调度器：

| 职责 | 最小变化 |
| --- | --- |
| 创建和登记 | 原生创建 Session，复用平台映射；明确创建与登记的重试边界，保留 preset、目录、Session ID |
| 消息接收 | 复用现有消息、任务、request 绑定事务；浏览器和宿主调用分别验证身份，再进入共同业务核心 |
| 内部执行 | 已绑定任务经可信执行上下文进入原生方法；不能再次提交平台任务，也不能靠客户端布尔字段绕过 |
| 查询和订阅 | 复用已有 owner 解析，把 page/follow 等委托给实际会话宿主；保留游标、错误、取消和流语义 |
| 网页网关 | 保留访问鉴权、代理和连接撤销；新能力下不再另做一次平台任务接入。浏览器身份须通过可信调用上下文传入，不能将全部网页请求降为宿主身份 |

现有 `RegisterDSHNativeChatSession` / `SendDSHNativeChatMessage` 依赖已授权的人类访问。不能原封不动给后台 IM 使用，也不能简单删除人类权限校验。需要把已验证主体与共同事务核心分离，这是必要的后端改动。

### 未修改 IM 的确切边界

已检查 npm `@xmanrui/dsh-im@4.23.0` 原包。其现代适配路径经 Typert Gateway 调用 create/prompt，并把 history 转为 follow/page；若配置了独立 Harness 地址或宿主提供旧 apiProxy，会选择其他路径，需要按实际启用配置分别验收。

- 现代适配器先获取 follow 快照，后续 page 使用缓存的 throughSeq；本地 `session/event` 才推进该缓存。仅路由 page 不足以读取另一个执行 Host 的新回复。隔离探针用原包适配器验证了这一行为；需要正式的事件回传及会话对象语义，不能伪造日志事件或放宽 throughSeq。
- ask 按自身 promptRpcId 对应的 user/message 与 turn/end 识别回复，默认无进展等待约 10 分钟，再查询 running。平台排队不能冒充原生运行，排队状态与原生 accepted 的语义需要单独实现和验收。
- 控制路径还会直接访问 `ctx.agents`，调用 Agent.cancel/inject/runMaintenance；审批、问答依赖宿主本地事件。它们不经过 sessionController，替换会话服务不能自动覆盖。

所以本方案能够确定的最小主干是“标准会话服务 + 复用现有平台核心”。跨实例事件回传是 IM 收到结果所必需的配套。完整停止/插话/审批兼容仍需明确宿主控制和交互扩展，不能对外承诺只替换一个服务便覆盖这些路径，也不能借此擅自扩成整个 AgentRegistry/AgentLoop 重构。

本节为代码审计与方案收敛；尚未改动实现、运行 DSH 或发布。两个隔离契约探针通过：Remote 子类方法标记保留、IM 历史游标依赖本地事件。它们不代替真实预发验收。

原生网页的特有转任务逻辑迁入同一公共服务。旧 Runtime 可按能力版本保留既有路径；新 Runtime 不能同时在网页网关与插件中重复提交。后台调用以受限宿主/绑定身份授权，不要求插件获得浏览器 Cookie，也不从调用栈猜插件身份。官方请求未携带频道原始消息 ID 时，只能保证该标准 requestId 的幂等，不能凭空声称具备跨 request 的渠道去重。

普通 DSH 环境保持原官方服务；受管环境启用后握手失败须报明确错误，不能回退直发。平台内部的已绑定任务通过可信执行路径校验并放行原生执行，不再创建任务；不能接受外部请求体里的 `internal=true` 作为绕过标志。

统一入口不表示所有操作都创建任务：create/fork/rename/reset 等处理会话映射和元数据；prompt 创建或复用任务；list/page/history/follow 校验权限并路由读取。每个 token 不重复入队或落一笔接入事务。服务不得把平台排队回执伪装成官方要求的原生执行完成。

## 需要补齐的能力

| 能力 | 设计 |
| --- | --- |
| 创建/复用会话 | 以员工、安装/账号、频道会话键持久化映射，返回平台和原生身份；重复请求返回同一映射，保留选定 preset 和工作目录 |
| 已有会话接入 | 微信已创建的空 Session 可在归属验证后按原 ID 登记；非空历史通过原生接口读取，不全量导入或重放 |
| 发送消息 | 把文本、图片/文件引用、时区等规范化为现有输入协议，复用消息/任务/DSH 绑定事务；不能把附件降级成占位文本 |
| 去重和重试 | 渠道稳定消息 ID 与安装/会话作用域生成或映射到持久 requestId；同键同内容复用回执，不同内容冲突；接口超时后查询原请求，不生成新请求 |
| 状态 | 区分平台已接收、排队、执行、完成/失败/取消；平台 queued 不能被解释为模型失败或原生完成 |
| 结果与历史 | 状态以本次 task/request 为准；历史和原生流按正确 Session owner 路由，返回原生内容。不能抓最后一条 assistant 消息，不能只看本地 Host idle |
| reset / new | 走现有 reset epoch 和会话映射更新，保持旧历史、旧任务结果隔离与幂等；核对 IM 实际命令覆盖面 |
| 取消与 steer | 复用已有能力；忙碌 steer 的未支持情况返回明确错误，不静默降级成 queue，不把取消单个消息变成杀 Host |
| 附件与交互 | 盘点 IM 实际调用的上传、审批/问答和流订阅接口；维持附件所属会话及交互所属任务，跨 Host 正确路由 |
| 管理辅助 | 健康检查、模型/preset/workspace 查询继续使用现有接口；为 IM 整理完整调用矩阵，不无故改管理逻辑 |

会话接口盘点还包括 list/search/page/follow、fork/rename/selectModel/updateQueue；每个公开方法标明直接复用、受管接入或所属 Host 路由。不能只接 create/prompt，然后把状态、结果、取消和附件留在另一条本地会话路径。

## 后端复用方式

把接入前的身份验证与共享事务核心分开：浏览器继续校验现有 NativeAccess；插件校验受限的后台接入身份。两者通过验证后使用相同的会话映射、权限复核、任务创建、绑定、幂等和锁顺序。不可删除现有 human grant 校验后让所有来源通行，也不复制一份独立的微信任务落库逻辑。

后台身份由平台依据员工、启用的插件/绑定、Runtime、Host generation 签发或确认，支持撤销和失效；不使用浏览器的 15 分钟 Cookie，也不把模型或用户 DWS 长期凭证写入插件配置。外部微信用户保留为渠道来源，不能当成平台成员 ID。执行的责任主体按授权绑定归属，沿用现有 agent-owned/频道身份策略，并在事务内重新验证绑定有效。

复用现有受认证的 Runtime 控制/反向传输机制承载调用；如扩展协议，增加能力握手和明确操作白名单。不同环境的 authority 不混用。请求体自报的员工/工作目录/Host 地址不能决定授权范围或路由。

## 必须处理的两个非发送问题

### 正确等待与回传

平台 receipt 保留在宿主适配服务内部，按 task/request 与原生 request 身份关联；客户端继续通过标准状态、history/page/follow 观察本次回复。接收 RPC 与模型执行等待分开，保留官方 accepted/queued/finished 的真实含义；重连后恢复同一 request，不把排队时间套入接收超时。

原生进程本地 idle 与平台 queued 不能互相冒充。第一阶段必须用未修改 IM 插件验证其实际等待逻辑能够通过标准协议正确工作；如果标准协议缺少它所需的排队状态或关联语义，明确提出通用接口缺口，不能伪造 busy、复制 assistant 历史或悄悄修改 IM 客户端。外部投递回执仍由频道插件拥有，宿主只观测其公开提供的结果；频道无幂等时不承诺绝对 exactly-once。

### IM 只由指定 Host 消费

先核对现有插件在员工多个 sandbox 上的加载范围。绑定相同账号的消费者不能在所有执行 Host 同时启动。最小方案将 IM 后台收件限定到指定入口/集成 Host，其他任务 Host 不启动同账号的接收器，但照常执行 DSH 任务。切换前确认旧 owner 已停止或失效，接收和提交使用 owner generation 及消息去重。

使用正式 Profile/插件作用域配置限制加载位置，并验证原生管理界面可用。若官方 IM 无法分离后台收件与管理，提出明确的通用配置需求，不擅自发布私有兼容包；不能假定禁用整个插件不会影响管理。该项是实际需要检查的风险，不表示已观测到重复收件。

## 验收与发布保护

- 微信真实发消息 -> 平台出现正确会话/任务 -> DSH 原生可见输入和回复 -> 微信正确读回，同一输入可追溯到全部身份。
- 原生网页与至少一个不依赖 Multica SDK 的独立标准插件，分别通过 HTTP/Remote/进程内会话 API 验证同一入口。标准插件不改代码仍可创建、发送、查历史和取结果，才证明不是 IM 专用方案。
- 连续消息、同消息重复、排队期间重连、任务失败、取消、new/reset、图片/文件和交互确认，分别验收。
- 角色卡、MCP、Skills、工具身份走既有执行链路并检查真实行为；平台 completed 不能代替业务成功。
- 插件升级/重启后账号绑定仍在、配置修订一致、能再次收发；多执行 Host 不重复消费或回复。
- 网页聊天、平台钉钉机器人、定时和子任务做受影响回归；保持前面 CR 的修复。
- 先部署兼容后端，再给指定预发 Agent 激活新能力；旧 Runtime 保持原路径，不能全局要求新协议或批量重启热 Host。
- 新链路故障停止新接入并保留已登记任务/回执；不以旧路径重发结果未知的同一消息。运行中的原任务不强杀、不换凭证。
- 观察任务失败率、最老排队时间、重复接收、结果投递未知和资源清理；不在生产赛塔上压测。

## 范围判断

这是一项宿主会话接入收口，规模小于全量插件化，但比 IM 客户端专用转发更广。关键工作是正式会话服务扩展、后台身份、共享事务、标准结果语义、跨 Host 路由与单消费者。保留现有“平台任务先绑定上下文再调用原生 prompt”的顺序，不重做组装和批次执行引擎。

标准 Session API 以外的任意 `agent.send/followup`、直接改私有 inbox 或日志文件不自动纳入透明兼容承诺；逐项盘点公开直接投递是否经过现有执行校验，不能允许缺少任务上下文的调用静默执行。若用户所需插件必须依赖未覆盖入口，明确列出缺口。接入失败可观测，不以扩大改造整套 AgentLoop 的方式偷偷解决。

公开服务替换及标准 Gateway 分发机制已由代码确认。尚待落实并验证：跨 Host 事件回传、排队与结果语义、IM 绕过会话服务的控制/交互路径、收件实例限定配置、后台身份与去重存储。不能提前声称已实现所有插件兼容。


## 实施中的代码确认

- 使用正式 Cordis isolate 组合：官方 session-controller 保留在命名作用域，继续提供原有浏览器资源和 Typert schema；受管插件提供全局同名服务并委托原生控制器。无需修改 IM 包、官方原型或私有字段。实际 Gateway、schema 和 isolate 单测覆盖分发与执行不重复入队。
