# Coordinator 连续对话与可靠回复优化

## 问题及基线

基于 aone/develop `b23920733` 创建 `codex/coordinator-contextual-replies`。正式trace `f2370cf3-6fe2-47d2-ade7-607ce03bcebc`（20:37:49 +08:00原消息）已投影 `mention_relation=includes_employee`，模型及审核仍用旧接收显示名/岗位人设把“你之前干啥去了”判成找别人，Host再硬编码回复“我在，看到你的消息了。抱歉，刚才没接上。”。另外两轮 `9444cc29-efc7-4cb0-af8b-85716a5ce719`、`f6aa8d4e-1d21-4e02-8a7d-5bf48290b4dc`同样重复。

现有group合同允许社交，但inbound/schema将ack限定成greeting/thanks/correction/receipt，正常追问与沟通反馈没有清晰动作入口。上次兜底证明了可见送达，没有证明正常对话已恢复。

## 方案

1. **可信收件人是Host事实。** 逐条投影response_required及稳定UID，不将人设/旧显示名当另一个收件人。直接单聊或可信@本人需要回应；合窗不串来源，他人群消息不自动取得响应资格。
2. **补齐受限社交动作。** 扩展acknowledge(conversation)，回应日常社交追问、对已见回复的反馈及抱怨。必须回应当前话意，按可见对话承接；不编造刚才在忙什么、现实活动或故障原因；业务答案、执行、状态继续走各自已有动作。
3. **先修正常判断，再用异常兜底。** 主模型/schema不再允许忽略必须回应的来源，Host与独立审核共享相同义务；在现有循环内修正遗漏，不靠成功ignore后固定文字覆盖。真正的预算/模型/持久化异常仍保留已有幂等outbox和自然失败回复，不依赖新模型保证底线。
4. **避免旧回复抢答与重复交付。** 工作动作的reply只承接工作，不提前贴完整产物；原文重发仍由单一执行交付路径完成。
5. 同步现行合同、policy版本/预算/来源映射及对照案例，不增加语言关键词分流或随机文案轮换。

## 预发验收（必须完整）

唯一真实订阅：冬翔→东翔测试号。群/配角不在订阅范围，不能误报为故障。发布基于新SUCCESS二进制，不借旧部署验证新代码。

- 连续多轮：问候→个人状态/前文追问→指出回复重复→换表达方式；每轮必须回答本轮话意，不能固定句循环或编造活动。
- 基于可见历史承认上一轮答非所问；对不可见的活动/故障原因保持未知。
- 能力问答不派发；进度基于正确工作状态、不重启。
- 新工作+谢谢不吞请求，新旧交付物正确区分；等待真实执行和同CID最终回读。
- 原稿重发准确且只交付一次，接单不提前贴全文。
- 受限/失败请求仍可见回应且不泄露内部reason；结构/故障单测覆盖真实模型不可用底线。完整E2E不以“收到”代替执行，不把局部通过写成全通过。
