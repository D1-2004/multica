# 交付提示词与 Skill 分层调整

## 目标与范围

用户要求核对 `multica-delivery-loop` 对效率的影响，结合实际轨迹优化项目提示词和相关 skills。只调整开发面指令和文档，不修改员工模型提示词、业务代码、运行时、部署或其他 session 的工作树。

## 发现与依据

- 原交付 skill 无条件串接“原失败→修复→部署→原场景复验→受影响回归”，缺少规划、代码审查和限时收口分支；用户要求的证据标准容易被解释为每次都跑完整真实链路。
- 第五批接续 00:43–07:00 三轮发布，发现的质量和观测问题不断进入同一收口；任务归属与执行方法、长期记忆与近期历史未在一次验收合同内先区分。
- 374 条命令、271 次执行调用、130 次代理消息/追加任务是此前时点主代理轨迹统计，不是浪费比例或因果证明。报告/共享进度落后版本与测试场域释放迟滞是已确认的重复协调因素。
- 性能 session 的通知切片未集成，计时缺口引出镜像重建；测量、候选完成与线上收益需分别交付。
- 审计依据是交付记录、两条工作会话的实际轨迹和独立审查。个人会话材料仅保留本机；临时运行版本与账号不固化为共享规则。

## 方案

1. CLAUDE.md 只放稳定入口与适用边界；项目工作流定义任务合同、验收模式、范围变化和唯一进度表。
2. 个人 `multica-delivery-loop` 只负责路由与关键决策，真实验收细节按需读取。
3. Aone / FC / LF / 通用 E2E skills 增加作用域与停止条件，查询不自动变发布，代码 review 不自动变 canary，取证缺口不自动变 Runtime 修复。
4. 保留部署事实、权限、场域、不可变来源、幂等和如实报告；不降低真实运行或上线的签收标准。
5. 用反例场景审查指令冲突，加文档链接和 skill 格式校验。无业务代码变化，不跑业务测试或新真实用例。

参考 OpenAI 的 [skills 与 prompts 分层建议](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)、[AGENTS.md](https://learn.chatgpt.com/docs/agent-configuration/agents-md)，Claude Code 的 [按需 skills](https://code.claude.com/docs/en/skills) 和 [独立 subagents](https://code.claude.com/docs/en/sub-agents)。采用稳定入口、渐进加载与隔离审查；不照搬某模型参数或扩大外部操作权限。

不承诺墙钟收益；本轮证明指令边界更清楚，真实效率需后续实际交付观察。

## 完成结果

- 根CLAUDE增加稳定路由；新增交付模式合同、条件化真实验收操作章与效率审计。
- 更新个人multica-delivery-loop、e2e-verification，以及仓库Aone、FC、两个LF skills。Aone长操作移至reference；收窄LF/E2E描述，避免普通session或业务ID误触发。
- 12例独立前向审查的行动计划符合场景；下层参考发现五项冲突，经修订与独立复核关闭。记录见 `docs/evals/delivery-instructions-review.md`。
- Markdown本地引用、6份YAML/name/description与diff检查通过。旧quick-validator拒绝三个原有compatibility字段，已验证与基线一致并记录，不改协议元数据来凑绿。
- 个人skill修改前副本保留在本机；仓库原版由Git保留。
- 本轮只改开发面文档/skill；没有提交、发布、业务测试、用户账号调用或员工模型提示词修改。主目录其他session WIP保持原样，未修改正在开发的交付树。

## 生效边界与遗留

个人skill已写本机文件；正在运行且已加载旧正文的session需再次读取新skill。仓库指令只在本checkout修改，其他worktree需要合入本批文档/skill后使用，不能声称已自动同步。旧validator的compatibility限制与真实效率观测留作明确限制，不阻断本次指令交付。

## 范围修订：共享规则与个人记忆分离

用户后续要求检查副作用，并统一AGENTS/CLAUDE提示词架构：本地开发模式、分支和提交偏好仅保留个人记忆；共享项目以E2E验收标准、测试环境、任务交付流程和有界人工接手为核心。

- [x] AGENTS仅统一入口；CLAUDE保留工程硬约束，新增通用交付合同入口。
- [x] 通用合同先定义E2E/环境/流程，再按里程碑交付；长期等待与模型语义缺证不得自动降为review通过。
- [x] Employee文档仅保留领域操作；个人轨迹与模式从共享规范移出，专项skills不预设某个开发者分支/profile。
- [x] 用提前交接、E2E替代错误、隐私阻断、个人配置缺失等反例审查副作用并验证引用。

不更改业务实现、工具权限或正在执行的其他session；既有工程/发布/Runtime硬门保留。

### 本次修订结果

新增全项目 `docs/development-delivery.md`；AGENTS去重为通用地图，CLAUDE加入统一入口，mobile/Coordinator仅接入共享合同，原领域约束保留。Employee工作流缩为领域检查；个人模式和原始审计留本机，项目不依赖个人skill。

FC文档取消固定个人分支/profile的示例绑定，Aone参考移除个人提交偏好。保持不可变来源、精确目标、权限、运行canary和滚动兼容约束。场景定义16条；本次4条新增请求经独立只读审查，发现的3处副作用全部经修订和定向复核关闭。

本轮验收为共享指令结构、引用、工程硬约束保留和前向文本计划；业务E2E不适用，因为未改变运行行为。没有提交、部署或同步其他worktree，不宣称运行效果或墙钟收益。

## 提交与远端整合

用户要求提交并推送。本批仅包含共享指令、仓库skills及其操作参考、交付文档和审查场景；个人skills留本机，其他session业务WIP不提交。

远端目标为当前分支的upstream `aone/feat/tag-multitenant`。本地checkout落后远端且有其他WIP，使用隔离工作树在最新远端上语义整合本批提交；交付工作流的旧详细操作拆至领域操作合同，统一入口与E2E/环境/有界交接规则采用本次修订。推送仅快进，不强推、不触发部署。文档结构/引用检查与审查结论随本批提交保留。
