# Coordinator 行为合同与渐进式上下文改造提案

状态：实施中。用户已授权优化、代码提交、预发部署及简单 E2E。日期：2026-09-07。

用户要求：保留历史翻车经验；实现上下文渐进式披露；以后修改 Coordinator 按统一守则进行；Coordinator 是数字员工在聊天里的反应，需要像人一样协作。

设计阶段产出：本方案，以及同目录 `2026-09-07-coordinator-progressive-context-inventory.json`。设计阶段未运行真实 IM 或部署；当前实施和验证结果见文末。源规则清单的结构完整性与行为正确性是两个结论。

## 1. 定位与不可交换的目标

Coordinator 是数字员工的即时对话与工作协调能力：判断是否接话，听懂当前意图，利用必要上下文回答或澄清，衔接已授权工作，给需要结果的人准确反馈，并在不需要时安静。它与沙箱是同一个员工的两种工作节奏。前者不发展成第二个通用执行运行时，后者继续使用现有 Multica 任务链。

优化顺序：不误执行、不漏请求、不串身份/场域、不虚报状态 > 对话自然、响应及时 > 上下文和调用成本。不能用 token 降幅抵偿漏单、重复执行或错误授权。

“像人”落实为八条行为义务：

1. 认清谁在对谁说话。DM / 直接 @ 表示可处理本会话，不能自动扩张为跨群传播或代别人承诺的授权。
2. 把当前这轮话听完整。保留各句作者、引用、补充和纠正；末尾“谢谢”不取消前面的请求。
3. 能回答就回答。可以由可信上下文恢复的对象先恢复，只在关键缺口仍阻塞时问一个短问题，不要求用户重复已提供的信息。
4. 理解“好”是在回答什么。对员工刚才问题的答复与普通收尾不同，不能按词表抹掉潜在授权。
5. 当前消息与已界定的上下文决定行动。同一交付物且有实质推进才续接；催促与重复原请求不等于再次执行；明确授权后不机械反复确认。
6. 接住的每项工作都有去向。回答、澄清、提交、等待和失败可区分，超额请求或部分成功不能丢失。
7. 用事实说进度。准备、排队、提交、送达、对方回答与最终完成分别需要证据；不把承诺当进展，也不把“曾经发过消息”当新结果已通知。
8. 说对方此刻需要知道的话。接单简短，清单完整，失败说明具体缺口；同一结果已送达就不再刷屏。人格决定措辞，岗位规则可收紧行为，Host 身份与权限始终有效。

参考 `dta-basic-behavior` 的语义原则，但不把其整份 Skill、Prepared Run 协议或运行模式搬入 Coordinator，也不改变本产品所有外部执行交给任务的边界。

## 3. 历史经验的保存方式

保留的是 Why 和行为义务，旧实现手段允许被替换。旧规则必须有继承关系，不能同时把相互矛盾的三代补丁列为现行规范。

例如 9 月 7 日修订撤回“忙时先等容量”和“排队就提前 sync-silence 结单”，保留的目标是：忙时能接话、工作不丢失、回执不虚报、同一请求不重复执行。

建立四类资产：

| 资产 | 职责 | 是否进运行时上下文 |
| --- | --- | --- |
| 源证据清单 | 保存 trace、提交、原句、事故与被替换的手段 | 否 |
| 现行行为义务表 | 每项稳定义务、适用条件、优先级、前置证据与执行归属 | 只编译需要的原则 |
| 提示词模块与工具合同 | 把生效义务装配到正确时机 | 是，按条件 |
| 行为案例与证据 | 验证正例、反例、披露路径和真实效果 | 否；少量必要例子可进入相关模块 |

建议每项义务至少记录：

```yaml
id: COORD.CONTINUE.SUBSTANTIVE
status: active
obligation: 仅当本条消息推进同一交付物时续接；状态询问不产生执行副作用
scope: inbound
incident_refs: [a6dcbb4d2, c18d8d0ff]
source_entries: [SRC-019, SRC-020, SRC-023, SRC-059]
requires_before_effect: [current_utterances, recalled_issue, continuation_evidence]
runtime_home: [core, recall_match]
enforcement_home: [host_reference_validation, semantic_decision]
case_ids: [status_vs_retry, same_person_different_work, answer_vs_ack]
supersedes: []
verification:
  source_mapping: reviewed
  host_checks: pending
  model_replay: pending
  live_delivery: pending
```

`semantic_decision` 明确表示还需要模型判断，不能因代码校验了引用 ID 就声称语义已由代码保证。`active / superseded / accepted_gap` 用于义务状态；证据不足另标 pending/BLOCKED。替代条目必须写原因与 `superseded_by`。未知原意的条目先保留并登记，不得为达到预算删掉。

## 4. 运行时结构：稳定核心、条件规则、按需事实

### 4.1 初轮必须知道的内容

常驻核心约束应覆盖第 1 节行为义务以及“什么信息不足时需要补读”的导航。不能把同交付物、授权、事实来源等基础边界全部藏进后续模块，否则模型会在不知道规则时就决定执行。

初轮输入包含：

- 可信 actor、scene、source、响应资格和当前窗口边界；正文、引用、附件元数据均保留为数据。
- 本窗口全部有序原文及每句稳定来源；只呈现一次，不把同一长窗口同时展开成两份 current_message/window_utterances。
- 简短人格、回复风格、可约束行为的岗位规则；岗位规则不能扩张 Host 授权。
- 已有的小型能力目录与稳定记忆卡。缺失必须有状态；少量事实不必为了“渐进”硬改成额外调用。
- 若已有可验证的未决问题，提供简短问题索引及可读引用。多项候选不能随意只留最新一个。
- 上下文目录：哪些资料已加载、哪些可按需取、scope/版本/覆盖范围是什么。

模块由 Host 按可靠条件选择：inbound/task_finished、web/robot/digital_employee、dm/group、多句窗口、是否已召回候选、是否具备某工具所需证据。不要靠“包含技能/会话/好”等词直接决定业务意图并裁掉证据。

### 4.2 披露阶段与副作用边界

| 阶段 | 规则与资料 | 可以做什么 | 不可越过的边界 |
| --- | --- | --- | --- |
| 当前对话 | 短核心、适用场景规则、当前窗口、轻量能力/记忆/待答索引 | 直接回答/澄清/沉默；请求相关上下文；召回事项 | 信息未披露不等于不存在，不直接猜续接目标 |
| 对话补齐 | 相关原问题、对象、时间、引用原文；缺口状态 | 理解短答、恢复对象、形成完整请求 | 后发问题不能为早先消息提供授权 |
| 事项匹配 | 候选卡、范围、状态、最近证据；同交付物判据 | 对合法候选读取详情；形成新建/续接/关联计划 | 召回命中仅为候选，必须有当前实质推进 |
| 受校验提交 | 整窗覆盖、各项来源与目标、幂等与已提交状态 | Host 经校验提交工作意图，返回实际结果 | 不在自由推理过程中边写边改决策；部分成功不可重放 |
| 任务完成回报 | 该工作的新结果、目标会话、送达状态 | 只读该工作，回答或沉默 | 不加载建单路由；旧阶段出站不代表当前结果已送达 |

这是同一个短循环的按需路径，不强制每个消息都经过五次模型调用，也不增加固定的“分类模型→主模型”前置链。简单能力问答仍应一轮完成。

初轮的工具只需覆盖直接终结、受控上下文读取、事项召回；工具详细定义随真实依赖解锁。召回后才披露合法目标的详情/计划合同。新建前的当前场景召回继续由 Host 检查。

第一阶段保留现有 API 行为，先拆分提示词与场景；完整的写工具收敛到计划/提交边界在独立阶段统一替换。不能只把 comment_add 改成非终结，然后任由模型在后续轮自由反复写入。

### 4.3 规则模块的依赖与寿命

每个模块登记 `id/version/applies_when/requires/owns_rule_ids/required_before_effect/budget`。在可能造成副作用的工具开放前，其安全依赖必须已在模型所见消息中出现；错误 hint 只负责参数修复，不能承担事前授权规则。

核心和已发生效果的凭据保持稳定。上下文读取返回数据，同时由 Host 注入相应的版本化规则片段；业务正文不能把自己提升为“必须遵守”的规则。相同模块不重复追加。不同任务/新窗口从其实际状态重新组装，不把上一轮临时错误说明永久写进记忆。

优先减少初始装配和重复追加，不急于删改已经对话中的证据。若需要中途收缩上下文，保留当前计划依据、合法 ID、关键否定/纠正、实际提交结果及必要工具调用/结果配对；每次记录新的有效上下文快照。不能靠仅删除上一轮 tool schema 来宣称已降低全部历史 token。

## 5. 事实上下文与对话焦点

所有可按需读取的块至少返回：`status / scope / version / as_of / complete / truncated / evidence_refs`。状态区分 `loaded / empty / not_loaded / unavailable / stale`，截断另标。`empty` 必须来自成功且覆盖相应范围的查询。

| 事实类型 | 权威来源 | 特别约束 |
| --- | --- | --- |
| 谁说了什么 | 可信入站事件及原文 | 显示名仅供展示；缺失身份不补造 |
| 上一问与短答关系 | 实际送达的原问题、提问对象、引用关系、时间 | 不是“最新一条问号”；同事相互对话不是对员工的同意 |
| 能力目录 | 已安装技能快照 | 完整性标记；介绍能力不能推断当前身份已有全部权限 |
| 稳定记忆 | 当前 scene 的已提交记忆及版本 | 当前纠正优先影响本轮理解；待写与已写分开 |
| 事项及进度 | 关联召回、任务状态、相关评论/执行证据 | 48h 不是全历史；自己的旧承诺不是实际进度 |
| 结果是否已告知 | 成功送达记录与结果关联 | 按工作、结果/版本、接收场域去重，不能仅按任意 outbound |

待答问题是控制状态或其可重建投影，不放进长期场域记忆交给 Flusher 管理。优先利用已有持久化消息/任务上下文推导；不足时持久化最小结构：问题证据 ID、scene、实际提问对象、交付物引用、缺失槽、时间、已解决/已替代状态。只有实际问出并送达的内容能构成待答问题。多实例必须使用共享持久化事实，不用进程内变量作为唯一来源。

历史按窗口中的原消息时间/顺序设置水位，不用重试时的 now 当原问题上界。保留 timestamp、source message ID、speaker、reply_to；源平台同秒消息还需 ID/序列消歧。封窗之后的新消息属于另一个窗口，不能倒灌成旧消息的授权。确需读取之后的执行进展时，以独立“后续状态证据”呈现，不能混为当前请求依据。

上下文裁剪必须按完整事实/消息块进行，关键引用与否定不能半句截断。超预算可以保留索引并声明尚有内容；记忆/能力“完整盘点”需读取完整范围或明确分页，不能只把已展示的部分说成全部。

按需历史是第二阶段性能优化：先保留原预读并修正时间/来源，验证对话承接；再比较按需方案在直接问答、短答、混合窗口的总延迟。目标不能只看一次读取少了多少 token，还要看是否多出模型往返。

## 6. 整窗先规划，效果再提交

当前关键限制：`issue_comment_add` 在 runLoop 中会实际写入并启动后续任务，成功立即整轮返回；`finish.items` 只表达新建。于是“旧事补充 + 新工作”“两条旧事续接”无法靠现有终结结构可靠覆盖。渐进披露必须以完整性为前提。

目标结构建议把内部决策分成独立的沟通与工作意图：

```text
WindowDecision
  speech: answer | acknowledge | clarify | progress | silence
  text: 一份覆盖本窗口的自然回复
  work_actions[]: create | continue | bind
    source_refs / delegator_ref / deliverable / target_ref / evidence_refs
  coverage[]: answered | clarified | planned | deferred | no_action
    source_refs / action_ref / reason
  unresolved[]: 原文依据与待解决原因
```

这些是拟议内部类型，不是要求本轮马上更改外部 API。业务取消、草稿、等待等意图仍按现有执行能力处理，不能因为新 schema 写了名称就宣称已实现。

完整性不能只按消息计数：一条消息可能有多个请求。原消息 ID 下的子请求保留文本范围/稳定 part 引用；Host 可检查引用有效、归属一致、范围未丢、各项去向存在，但不能靠结构检查证明模型已识别全部语义，仍需“一句两事”和多句混合的模型回放。

提交规则：

1. 先确定身份、附件等 Host 条件，再进入判断；提交后不把动作覆盖成另一路派发。
2. 提交前检查所有来源、目标、必需证据、窗口覆盖与当前授权范围。语义匹配仍由模型负责，不能用测试探针 token 的匹配冒充自然语言守卫。
3. 同一窗口计划按现有数据库事务边界持久化，工作项各有稳定幂等键；关联、评论、入队沿现有正常路径处理。一次数据库提交不等于一次外部 API 执行。
4. 记录未提交/部分提交/已提交；使用已有 `issue_results` 回传真实创建、评论、执行 ID。某项失败不能擦掉先前成功结果，也不能把整个窗口从头重做。
5. 规划覆盖整个窗口，但提交批次最多两项。超过两项时，先以稳定子请求 ID 将余项原样持久化为后续窗口/批次，再等待本批最多两项所需容量；不能让三个执行项一起等待永远只有两个的槽位。保留每批的现有容量保护，不把拆批变成每次恢复都重新自由识别原文。余项未持久化不能结束本轮；接待回合的收口不表示各批工作已完成，父窗口保留所有子请求去向。
6. 等待、重试仍保留窗口原始请求；恢复时重新校验实时执行状态和撤销/替代关系，但不能拿后来历史改写最初授权。
7. Router 回执与子任务回调继续分离。保留现有独立 Issue 上下文，工作排队不能提前报完成。
8. 不承诺端到端绝对 exactly-once；数据库幂等、outbox、下游去重和不确定写入回读各自负责，按实际支持验证。

## 7. 故障与预算的处理

有限轮数和墙钟预算保留。上下文读取前检查剩余预算，为一次参数修复和合法终结预留空间。单纯“第 8 轮只剩 finish”可能使仍需证据/提交的工作无路可走，需要与新的提交合同一并修订。

故障不能扩大授权：

- 已知的能力问答、在场回应，不因历史读取失败自动变成沙箱任务。
- 指代/授权证据缺失，保留原文、有限重试；能向用户提出有效澄清时澄清，不编造对象或同意。
- 已接受的工作继续幂等恢复；已提交部分不重放。
- 真实权限失败可以如实说明。应禁止的是把“Coordinator 没该工具”误说成员工永远办不了，而非全面禁止“无权限”这个事实。
- `silence` 是有意不打扰；`deferred/failed` 是处理状态。二者分别记录，不能用 silence 伪装故障或丢弃待办。
- 已确认需要送达的新结果，靠可靠投递链恢复，不靠每次模型重复生成“已完成”。

## 9. 未来修改 Coordinator 的守则

建议以 `docs/inbound-coordinator-loop.md` 为现行合同，根 `CLAUDE.md` 保留短入口指针。新增 `server/internal/service/inboundcoord/AGENTS.md` 指向该合同与规则目录；根入口同时点名 handler、assoc、scenememory、trace 的 Coordinator 相关修改，防止只改 handler 就绕过规范。不要把长守则分别复制进多个入口。

新增版本化规则目录建议放在 `server/internal/service/inboundcoord/policy/`。目录登记规则 ID、模块与依赖；正文由独立文本资源提供，元数据不能重复抄正文形成双写。实际事故与回放放 `docs/evals/`，执行器靠近对应代码或仓库 scripts，按现有命令入口接入。

未来每次变更遵循以下步骤：

1. 写清“用户在什么上下文说了什么；当前发生什么；希望发生什么”，关联义务 ID 与事故证据。区分措辞、语义、取数、工具或状态机变化。
2. 先看现行义务，再看历史。新补丁覆盖旧规则时写替代关系；不因旧测试通过就恢复已撤回机制。
3. 指定唯一主要归属：核心、条件模块、工具合同、Host、上下文读取或案例。禁止默认追加 systemPrompt 末尾；依赖关键语义的规则也不能全部搬到离线案例里。
4. 新增、合并、迁移、删除每条规则都有去向。无法解释历史原意或证明替代覆盖时登记未决，不能为成本指标删除。
5. 对需要模型判断的改动提供最小对照：同一句话只改变一个上下文条件，并写明允许与禁止的副作用、应读上下文、应保持的一轮直达路径。
6. 审查披露依赖：规则是否在决定/副作用前可见；隐藏它的触发条件是否可靠；取数失败、截断、重试和旧窗口是否仍安全。
7. 同一变更同步更新工具 schema、hint、返回投影、Host 守卫、当前合同、受影响案例和观测字段。修改一个面不得留下相反的另一个面。
8. 验证分层且如实标记。确定性代码检查、脚本预置模型响应、真实模型回放、真实投递证明分别记录，不互相替代。口吻小改用受影响案例抽查；窗口、身份、授权、续接、送达、幂等改动使用对应集成与业务证据，不要求无差别全仓测试。
9. 临时事故保护记录误伤对照、作用域、负责人、替代方案与移除条件；它不能默默变成员工永久人格。
10. 发布记录精确策略版本与装配版本，回滚以现行义务为基线；不可通过恢复旧 busy/ACK 补丁重新引入已知漏响应。

建议提供一个轻量 `coordinator-policy-check`，由正常检查入口调用。它检查：规则 ID 唯一；活动义务有归属与案例引用；删除有替代或明确批准的行为变更；模块依赖闭合；每个有副作用的出口声明所需前置；新增原句是否绕过目录；现行文档版本是否一致。检查器能证明元数据闭合，不能证明自然语言判断正确。

检查器应识别改动风险而非锁旧文案。现有 `strings.Contains(prompt, 原句)` 改为规则/模块/依赖检查；scriptedCompleter 继续验证 Host 协议，但其通过不能写成模型语义验收通过。

## 10. 最小行为回放集

每个场景同时断言行为与披露：加载了什么/没必要加载什么、轮数、读操作、创建/评论/外发数量、原文覆盖和送达状态。不能仅比最后一句文字。

| 对照场景 | 预期行为与效果 |
| --- | --- |
| “你会什么” / “用这个 skill 整理这场会” | 前者直接能力介绍、0 工作；后者形成真实工作，先召回；不只复述能力 |
| “现在按这版发吗？”后的“好” / 最终结果后的“好” | 前者按已定范围继续一次；后者无新执行、不打扰 |
| 群友相互“三点行吗/行” / 员工向此人询问后的“行” | 前者不插手；后者只续对应交付物，真实作者不变 |
| “给须莫发条消息” / “就说明天下午三点开会” | 第一轮无空工作、追问内容；第二轮恢复对象后执行，不重复问 |
| “怎么还没好” / “刚才失败了，权限已恢复，再试一次” | 前者只读进度、无新执行；后者检查已有效果后按明确范围重试 |
| 同人问洗脚时间 / 新问打球时间 | 两份交付物，不能因同人或单一卡片强制续接 |
| 跨天明确答旧问题 / 跨天“你好” | 前者可有证据地续接；后者不自动重启旧工作 |
| 分句请求 + 后续条件 + 谢谢 | 一份完整工作，感谢不取消、不多建 |
| 旧事补充 + 新工作 / 两条旧事续接 / 同句三件事 | 全部子请求有去向；终结不丢后项；超两项持久化等待 |
| 两人各提一事 / 两人推进同一事 | 每项来源归属正确；同事补充不冒充另一人的授权 |
| “有哪些记忆” / “有哪些事没办” | 前者用完整稳定记忆；后者用事项，不能互相代替 |
| 撤回事实后再问 / 历史仍有员工旧复述 | 不复活撤回事实；待写与已提交状态准确 |
| 明确另一个 cid / 仅说本群的记录 | 使用相应作用域；历史、记忆、召回不能跨场景替代 |
| 引用“这个文件”且有稳定对象 / 读取失败 | 优先恢复真实对象；失败与不存在分开，不乱派或要求重复提供已有对象 |
| 两槽忙时“你在吗/你干了吗” / 第三项真实工作 | 对话及时判断；只有执行等待；4 秒/12 秒窗口与原回执保留 |
| 旧窗口重试时新增一条员工问题 | 旧“好/催促”不能借后来问题变成授权 |
| 同一结果已发本群 / 只问了联系人 / 新答复尚未回报委托人 | 第一种不重复；后两种按新增事实与送达需要回报 |
| 工具参数错 / 读历史失败 / 模型预算耗尽 | 最短修复或保留未决状态；不凭错误新建任务，不虚报正常沉默 |
| 第一项已提交、第二项失败后重试 | 保留真实 outcome，第一项不再提交；回执与剩余状态一致 |
| 员工出站消息 / 真实对方回信 / 引用员工旧消息 | 自发去重不自激；真实回复正常处理；引用不伪造新授权 |
| “写条消息先别发” / “把刚才那版发出去” | 岗位/用户限制有效；草稿无外发，后者有明确定稿依据才发送 |

自然语言样本必须去掉测试探针 token 后也能通过；不得只靠 `token=W2` 前缀把交付物匹配测成字符串匹配。对关键错误族既保留原事故样本，也有最小正反例及故障/重试变体。

真实回放使用脱敏、冻结的消息与上下文，写工具替身只收集计划，不向任何人发送。需要新真实 IM 验收时另在已授权范围执行；回读权限、环境或数据不足标 BLOCKED。已有 collect 记录仍是 0/3 真实轮次，不能在本次提案里改成 PASS。

## 11. 分阶段实施与退出标准

| 阶段 | 变更范围 | 退出标准 |
| --- | --- | --- |
| P0：冻结与建账 | 合并真实部署与本地基线，拆原句为义务，索引所有历史面，建立替代关系 | 源条目 100% 有解释；活动义务 100% 有归属/案例/证据状态；未决项显式列出，不能宣称闭环 |
| P1：合同整理 | 先接最小版本/模块观测；更新现行文档、模块指针、短核心、inbound/task_finished 分离、工具文案去重；保留取数/派发路径 | 老路径效果不变；受影响规则、工具依赖和事实来源一致；受影响案例回放通过；不存在同义反向规则 |
| P2：对话证据 | 先保证读失败不扩大执行、预算不足保留未决、已有效果不重放；再修 ACK 裁剪、时间水位、来源/缺失状态与待答问题；最后切按需历史 | “好”的两种含义、重试时间、多句补充、引用恢复及读取故障回放通过；简单问答保一轮；全链延迟不因额外往返恶化 |
| P3：完整窗口与提交 | 建立每项来源和覆盖，收敛新建/续接/绑定提交，前移附件条件，超额拆批与分项恢复 | 新旧混合、多旧续接、三项及更多请求、部分成功/重试回放通过且无漏项/重复效果；无超两项整批等待死锁；多副本与滚动合同验证 |
| P4：完成与故障收口 | 按结果/场域送达去重；移除误伤黑名单；补齐其余故障与投递恢复 | 新结果不被旧出站压掉；旧结果不二刷；相关回放及投递验证通过；错误不扩大执行、不静默丢请求 |
| P5：固化与渐进启用 | 完成全量检查器、综合影子比较与推广；每阶段已具有版本观测和受影响回放 | 历史义务证据达标；关键错误无新增；行为收益和成本一起报告，保留恢复方案 |

P2/P3/P4 涉及核心链路与状态机，应分提交、各自更新 Plan，不能与纯 prompt 整理混在一次无法归因的发布里。某个已知缺陷的修复可以前移，但必须单列行为变化与回放结果。首次运行时缩短 prompt 前，至少完成 P0 的有效义务映射；不能先删再补历史账。任何阶段独立发布前均需有相应观测与回放：P1 起记录策略/装配版本、提示词哈希、模块与可用工具；P2 加时间水位和缺失状态；P3 加窗口覆盖和提交结果。不能等 P5 才能解释前几次变更的行为。

性能目标先作待测预算：直接问答总输入 2,000–3,000 tokens；短核心约 800–1,200 tokens。以实际模型计数为准，工具 schema 与所有模型轮次一并计算。该范围不是承诺、不是验收事实；复杂请求只加载必要资料但不牺牲完整性。

每轮保存 `policy_version / assembly_version / prompt_hash / active_rule_ids / modules / context_source_refs / scope_and_watermark / loaded_and_missing / allowed_tools / model_rounds / input_usage / outcomes / coverage`。日志使用稳定理由码与简短说明，不要求输出隐式思维过程。记录实际装配后的历史数量，不使用预读前的 metadata 误报。身份、凭证与隐私内容按现有日志规范处理，不把秘密写入提示词版本记录。

上线前分别报告三种覆盖：来源迁移覆盖、义务/披露路径覆盖、行为证据覆盖。前两项全满不能替代第三项；任一未验证高风险义务都不能被一份低 token 报告掩盖。
