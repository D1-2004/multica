# ASB 容量回收启动延迟优化

## 目标与证据

金龙 Agent 的人工任务在 2026-09-07 正式环境排队约 8 分钟。SLS 显示两个 Runtime 共用 ASB 额度，每次回收查询约 1,680 条历史候选，逐个请求大量已 Terminated 的沙箱，一轮持锁耗时 77–81 秒。

## 实施方案

1. 容量回收使用已取得的 ASB 实时清单作为数据库候选过滤条件，历史记录不再触发逐条远程查询。
2. 删除前持有原有 scope 锁，仅按当前 sandbox ID 复查任务状态，避免反复全量查询。
3. 保留 stale 记录的原有含义、任务终态保护、聊天宽限期及租户锁；清单缺项只延后回收，不能作为删除历史记录或实例的依据。
4. 增加回收耗时和实时候选数量日志，支持预发对照。

## 兼容与边界

- 仅服务端与 sqlc 查询变更，无数据库迁移和 Runtime/Daemon 协议变化。
- 未传可选 sandbox ID 过滤条件的现有调用保持原语义，新旧副本可以滚动运行。
- 仅发布到 Aone 预发流水线 66；不修改正式资源或金龙 Agent 配置。

## 结果与遗留

- 隔离 PostgreSQL + HTTP mock：1,680 条历史记录，历史 GET 为 0；活沙箱 GET 为 2，安全回收 1 次；第二轮空清单无额外 GET，全部记录保留。该结果验证调用数量，不代表真实 ASB 网络耗时。
- 容量回收、聊天宽限期、忙碌/外部实例保护、容量等待与恢复专项测试全部通过；`go build ./cmd/server` 和 `git diff --check` 通过。
- 当前仓库直接 sqlc 生成受已有迁移顺序影响：271 引用尚未按文件顺序建立的 task_completion_outbox。因此使用本地数据库 schema-only 快照和 sqlc v1.31.1 生成目标查询文件；生成差异仅包含本次过滤条件及参数。
- 预发发布进行中。
