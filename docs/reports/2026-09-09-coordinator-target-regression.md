## 结论与验收状态

关闭入站 `issue_get / issue_comment_list` 确有信息损失风险。正确边界应是保留协调所需的目标、约束、执行与提交状态，业务报告全文由执行 Agent 按任务读取。关闭两个工具本身不代表问题解决。

本次确认三个根因：有限动作被误用为独立工具和字段错填导致反复拒绝；技能目录只有托管占位描述，导致岗位业务对象被旧事项标题替代；事项状态、执行状态和本轮派发数量缺少独立事实来源。审核也存在错判，不能以审核 allow 作为业务通过证据。

修复分支：`codex/coordinator-reply-recovery`；CR：`36057190`。最终预发部署、固定候选模型回归、真实消息验收结果待本轮补齐，本节不作为已部署证明。

## 修复设计

- 语义动作集合保持有限。已知动作误作工具仅归一到 `finish.actions` 候选，再走原来的来源、续接、授权与审核守卫；不恢复通用reply或未知写工具。
- 工作intent仅做窄分类修正，不自动改变basis或补造授权。审核协议错误最多在同一独立上下文、同一12秒期限内修正一次。
- 当前选中发言的原引用、作者和证据ID由Host交接，减少依赖模型重新抄写。原引用是数据，不是新增指令。
- 技能目录遇到空/明确托管占位，只读取最多4096字符的完整frontmatter，提取用途；保持每项80字与总1200字预算。
- `work_state.latest_execution` 独立返回最近执行状态；与Issue状态并存，completed不能证明外部送达。
- `context_read(kind=coordination_state)` 按Host当前job、workspace、agent和场域读取前3个协调窗口，区分计划数、持久提交确认数与未知。它不满足history原问门槛，也不代表整个会话全部任务。

读取快照保持8000字总预算；新协调状态最多2000字、查询最多2秒。没有恢复旧报告全文，也没有通过增加循环轮数解决故障。
