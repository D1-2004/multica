## 结论

先做一个 **PostgreSQL 属性图 + 带时间窗的召回查询**。不上图数据库。v1 粗排按时间/场域/关键词；**精排交给 LLM**。

平台上的「事」就是 **Issue**。图节点不叫 Matter，叫 **Task**（表名 `assoc_task`，避开已有 `agent_task_queue`）。每个 Task **挂在一个 Issue 上**：已有正在执行的 Issue，或当时新建的 Issue。Issue 通过索引路由到 Task。

`chat_session` 以后会少用，本层 **只做和 Issue 的关联**，不把 Multica session UUID 当图主键。

本层负责：

1. 落 Event、写边。出站优先 **单聊 cid 绑定**（人不绑也可以）。**派发 Issue/Task 时** 才把 Event 挂上。
2. 召回 API（必带时间；purpose 写清楚；支持简单 keyword FTS），同一套合同给 CLI / 沙箱 / Loop 工具。
3. 对外人员、会话用 **钉钉 ID**。Issue 用平台 identifier（`MUL-123`），Task 是挂在 Issue 下的图节点。
4. 边属性可动态加（又委托一个人不必改表）。「这是新事还是问旧事」由 **Coordinator 提示词** 判断，本层只返回候选。

黄金用例（必须能跑通）：

> Agent 为预约日程主动私聊 A、B。A/B 在新对话里回复时，系统知道这条新对话是因为预约才发起的。

这条路今天是断的。审批回调的「关联Issue」是显式 ID 通路；主动 `dws chat message send` 出去的私聊，回信时 **没有事边**。

## 背景：MOA 文档里我们真正该落地的那一层

《MOA：面向数字员工的 Managed Agent Architecture》的核心是双循环：

- **Event Loop / 快循环**：钉钉消息、群、@、审批、表格变更。低延迟、短上下文。判断「要不要回、回什么、要不要变成事」。
- **Task Loop / 慢循环**：Goal / Plan / 依赖 / 产物 / 重试。绑定 Durable Task，不绑定某一条消息。

文档把 Event → Task 的门槛写得很清楚，和你的补充一致：

> 消息、审批、表格修改首先是 Event。只有经过 **显式 ID**、**Scene + Active Task**、或 **语义判断** 之后才进入 Task。
> Event 是「发生了什么」，Task 是「接下来要持续完成什么」。

Coordinator 看的是一张图：当前场域里有哪些事、哪些对话是因为某个 purpose 主动找上门的。会话本身也可以是一个 purpose，会再派发出去一批事件。

本方案提供图和召回查询。Coordinator 快循环已在 `inboundcoord` 落地（`assoc_recall` / `assoc_bind` / `finish`）。图仍只返回候选；「新事还是旧事」由 Coordinator 提示词判断。沙箱以 Issue 执行时，用同一套查询回答「这件 Issue 下面有哪些 Task、已经给哪个会话发过消息」。快循环要挂的 Issue 查询/评论工具、以及召回 JSON 如何给 LLM 精排，以 [Inbound Coordinator Loop](/evals?tab=evals&doc=docs%2Finbound-coordinator-loop.md) 为准。

## 现状缺口（对照仓库）

| 已有对象 | 实际角色 | 对「事图」的缺口 |
|---|---|---|
| `issue` | 平台上的「事」（看板、状态、指派） | **就是承接对象**。缺的是「事 ↔ 钉钉 cid / 出站消息」的图，不是再造一个 Matter |
| `chat_session` | Multica transcript | **本层减少依赖**。群 binding key 是 `{cid}:sender:v1:{hash}`，不能当场域键 |
| `channel_chat_session_binding` | IM 流 → chat_session | 只管回复路由，不管「为什么聊」。图绑 cid → Issue/Task |
| `agent_task_queue` | 一次执行 run | 仍是 run。图上的 Task（`assoc_task`）挂 Issue，可再指向某次 run，不是取代 queue |
| Router continuation | 同一条会话的续写 | 新 cid 上没有 continuation |
| 审批 `关联Issue` | 从表单字段抽出 identifier，改写 continuation | 只有显式 ID；主动私聊没有表单可写 |
| `task_message` `tool_use` | 沙箱工具调用流水 | 刚删掉 DWS reply tracker（它曾被当成完成事实源）。观察 tool_use 做 **副作用绑边** 可以，但不能再当完成语义 |
| people-group-memory | Person / Conversation 叙事档案 | 记「他是谁、这群干嘛」；不是运行时事边 |

关键实现事实：

- DingTalk DM 的 session key = `openConversationId`；群 = `cid + sender`（`server/internal/integrations/dingtalk/resolvers.go` `dingtalkSessionRouting`）。
- 入站走 Agent Dispatch V2 → `createAgentDispatchChatV2` → channel engine `EnsureSession`。对方从新私聊回信 = 新 cid = 新 `chat_session`，与发起预约的那个 Chat/Issue **无边**。
- 出站 `dws chat message send --conversation-id …` 发生在沙箱或未来的 Coordinator Loop 里，服务端目前不捕获「发给了哪个 cid」。

所以黄金用例失败点就一处：**出站时没把钉钉 cid 写到当前 Issue/Task 上；回信进来时没有边可查。** 出站 v1 优先单聊 cid，人可以后补。

## 对象定义

「事」= **Issue**。图上再挂 **Task**（`assoc_task`），不要叫 Matter。

```text
Person? ──(可选)──►  Scene (钉钉 cid)
                       ▲
                       │ outreach / spawned_from
Issue  ←──  Task  ←── Event
（事）     purpose     发消息 / 回复
           动态 props
```

### 1. Person（人）

钉钉侧稳定身份，**不是** Multica `member`（被约的人常常不是 workspace 成员）。

- 主键：`(workspace_id, agent_id, platform, person_key)`
- **对外 `person_key` = 钉钉 `uid`（十进制）**。`openDingTalkId` / staffId 只进 `person_alias`，召回入参两种都可以，内部归一到 uid。
- 不把 Multica `member.id` / `user.id` 当召回键。被约的人常常不是 workspace 成员。
- 单聊的「对方」可以记在这里，但 **v1 出站不强制绑人**，有 cid 就够召回。

### 2. Scene（场域）

人能看见、能说话的地方。v1 只做 IM：

- `kind`: `dm` | `group`（后续可加 `aitable` / `approval` / `doc`）
- **对外 `scene_key` = 钉钉 `openConversationId`**。禁止用 `chat_session.id` 或群的 `cid:sender:v1:hash`
- **不存 `chat_session_id`。** 图只认 cid ↔ Issue/Task

群仍是独立 Scene。v1 出站绑定 **先做单聊 cid**，人不绑也可以。

### 3. Issue（事）+ Task（图节点）

平台上的事就是现有 **Issue**。不再发明 Matter。

**Task**（表 `assoc_task`）挂在 Issue 上：

- 已经在某个 Issue 下执行 → Task 挂这个 Issue
- 还没有 Issue → **新建 Issue**，再挂 Task
- Issue → Task 必须能路由，索引 `(issue_id, status, last_touched_at DESC)`

它不是 `agent_task_queue`（那是一次 run）。需要时 `assoc_task.run_id` 可空指向某次 run。

字段：

- **`issue_id` 必填**
- **`purpose` 必填且写准**：主语 + 要交付什么 + 范围。例：`预约A与B本周五下午30分钟`。禁止 `帮我约一下`。召回和 LLM 推理都靠这句
- `status`: `open | waiting | done | cancelled`
- `intent`：如 `calendar.book`
- `props jsonb`：动态可扩展。又委托一个人 = 加边 + merge props，不改表
- `agent_id` + `workspace_id`
- `run_id` 可空
- 预留 `embedding vector NULL`（v1 不写）

创建时机：Agent 显式开 Task 并落到 Issue。不从每条消息自动开。「新事还是问旧事」归 Coordinator 提示词。

### 4. Event（事件）

只增日志：「发生了什么」。

- `source`: `inbound_im` | `outbound_im` | `approval` | `calendar` | `aitable` | `tool`
- `direction`: `inbound` | `outbound`（回复和发出去都记，靠这个识别）
- `evidence_id` 唯一：`openMsgId` / 工具回执 id。同一条消息重放只 touch，不插第二行
- `occurred_at`
- `scene_id` 可空（钉钉 cid）；`person_id` 可空（v1 出站可以不绑人）
- `task_id` 可空：**派发 Issue/Task 时** 才回填

Event 不是 Issue，也不是 `agent_task_queue`。未挂上就保持空，让 Coordinator 决定澄清、忽略，还是开新 Task/Issue。

## 边：带属性的事边，不是 KV cache

一张 `assoc_edge`，有向、有类型、有状态、有属性。

```text
assoc_edge
  workspace_id, agent_id
  src_type, src_id     -- person|scene 的 id = 钉钉 uid / openConversationId；task/event/issue 用内部 uuid
  dst_type, dst_id
  rel                  -- 封闭枚举，见下
  status               -- open | dormant | closed
  props                -- jsonb，**可动态加键**，有大小上限，不改表结构
  opened_at, last_touched_at, closed_at
  opened_by_task_id    -- 哪次 run 写下这条边（沙箱绑定的审计）
```

v1 `rel` 封闭集合（不够再加，禁止自由字符串当关系）：

| rel | 语义 | 黄金用例 |
|---|---|---|
| `task_issue` | Task 挂在哪个 Issue | Issue 路由到 Task |
| `task_scene` | 这个 Task 发生在哪个 cid | 预约 ↔ 与 A 的私聊 |
| `task_person` | 涉及的人（可选） | 又委托一个人就再加一条 |
| `outreach` | 因这个 Task 主动发到这个 cid | send 成功；v1 只要求 cid |
| `waiting_on` | 在等这个 cid/人回复 | 发出去之后 |
| `spawned_from` | 这个 cid 因该 Task 派生 | 新私聊绑回 Task/Issue |
| `event_of` | Event 属于哪个 Task | **派发 Issue/Task 时** 回填 |

`props` 和 Task.props 都是 **可动态扩展的 jsonb**，不是死 KV cache，也不是改表才能加字段。

约定：

- 已知键（`conversation_id`、`open_msg_id`、`intent`、`expires_at`）Go struct 读；**未知键保留**，merge 进对象，不丢。
- 又委托一个人：插入 `task_person` + `outreach` 边（有 cid 就绑 cid），`props` merge `{delegated: true}`。不需要 migration。
- `jsonb_typeof = object` + `pg_column_size` ≤ 8KB。
- 提供 `assoc bind` / merge API，按键浅合并，不整包覆盖。
- 不在 DB 加 FK / CASCADE。
- 索引（各文件 `CONCURRENTLY`）：
  - `(agent_id, dst_type, dst_id, status, last_touched_at DESC)` 按 cid/人召回
  - `(issue_id, status, last_touched_at DESC)` **Issue → Task 路由**
  - unique `(agent_id, src_type, src_id, dst_type, dst_id, rel) WHERE status = 'open'` 开边去重

这就是「边能带属性、又比图数据库便宜」的最低形态。

## 召回：查询与关联分开；查询必带时间窗

两件不同的事，不要混在入站热路径里：

| | 查询 Recall | 关联 Associate |
|---|---|---|
| 何时 | Loop / CLI / 沙箱随时可调 | **只在派发新的 task/issue 时**，以及出站 send 成功写 outreach 边 |
| 写库 | 只读 | 写出站边、派发时写 `event.task_id` / `event_of` |
| 延迟 | 必须有保障：时间窗 + 覆盖索引 + `limit` 上限 | 可跟一次 dispatch 走，不挡 IM ACK |

测试标准不是 PageRank，而是人会怎么想：

> 「我刚为了约时间私聊了张三，他现在回我了——那就是那件事。」

### 查询必带时间

人最快的反应是最近几件。API **必须**带时间，禁止无窗全表扫：

- `since` 必填（绝对时间或相对，如 `24h` / `48h`）。缺省由调用方传，服务端若收到空值直接 400，不默默全量。
- `until` 可选，默认 now。
- `limit` 默认 20、硬顶 50。
- 排序：`last_touched_at DESC`（最近优先），同分再按 `rel` 权重。

Loop 工具和 CLI 都走同一套参数。

### 瀑布（查询侧排序，不是静默写边）

1. **显式 ID**  
   `--current-issue` / `MUL-123`，或审批正文里的关联 Issue。这是已有通路。

2. **场域 + 时间**  
   `--conversation <openConversationId> --since 24h` → 该 cid 上仍 open 的 Task / Issue。只用钉钉 cid。

3. **人 + 最近 outreach（可选）**  
   `--person <uid>` 不是 v1 出站绑定的前提。有人再过滤；没有就靠 cid。

4. **关键词 FTS（给 LLM 工具用，v1 就做）**  
   `--q 预约周五` 在时间窗内扫 `purpose`（及可选 Event 短摘要）。见下一节。粗排仍是时间；**精排是 LLM**。

5. **Embedding**  
   列预留，v1 不跑。

### 打分（第 3 步内部，~50 行 Go）

```text
score = exp(-Δt / τ)           // τ ≈ 6h
      * status_boost           // open=1.0, waiting=1.1, dormant=0.3
      * rel_boost              // waiting_on=1.2, outreach=1.0
      * same_agent             // 硬过滤，不是加分
```

工作集 = 时间窗内该 Agent 的开边，通常几十行。SQL 取出后按时间粗排，完整 `purpose` 交给 LLM 精排。

### 关键词 FTS：可以做，PG 有现成能力

人、事的 `purpose` 需要能被 LLM 工具搜。**默认 `to_tsvector` 英文分词，中文「预约周五」几乎不能用。** 本仓库 Issue 搜索已经走了 CJK 路径：

- `pg_bigm` GIN + `LIKE '%keyword%'`（migration `032`，`DO $$ EXCEPTION` 包起来）
- 没有 bigm 时 `pg_trgm` 兜底（`137`–`142`，同样包起来）

Task.`purpose` **复用同一套**，不新造搜索引擎：

1. 先用时间窗 + cid/issue 把候选收小（有索引，快）。
2. 再在候选上 `LOWER(purpose) LIKE '%'||q||'%'`。窗内几十行时即使没 GIN 也可以。
3. 有 `pg_bigm` 再给 `purpose` 建 `gin_bigm_ops`（单独 `CONCURRENTLY` migration，失败就 NOTICE，和 Issue 搜索一样）。

`--q` v1 **实现**，不是 reserved。purpose 写不准时 FTS 和 LLM 精排都会废，所以 purpose 写入要有最短长度/格式约束（建议 ≥ 8 个可见字符，且不是纯「帮我看看」这类）。

| 列 | v1 | 以后 |
|---|---|---|
| `last_touched_at` | 主过滤 + 粗排 | 仍是第一刀 |
| `scene_key` | 主过滤（单聊 cid） | 仍是 |
| `issue_id` | Issue → Task 路由 | 仍是 |
| `purpose` | 展示 + `--q` LIKE/bigm | 给 LLM |
| `person_key` | 可选过滤 | 仍是 |
| `intent` / `status` | 写入，可过滤 | 条件查询 |
| `embedding` | NULL，不建向量索引 | 语义召回另开 |

### 开源库调研结论（为什么不引）

| 候选 | 结论 |
|---|---|
| Apache AGE / PolarDB `polar_age` | PolarDB 上 `CREATE EXTENSION` 对应用角色是 42501，AGE 还要工单/高权限；1–2 跳召回用不上 Cypher |
| Cayley | 已停更 |
| Neo4j / Dgraph | 新基础设施，Aone 预发没有 |
| gonum/graph | 内存算法库，不负责持久化 |
| pg_knowledge_graph 等扩展 | 同样撞扩展权限 |
| 自建 SQL + 薄 Go 包 | **采用**。召回是业务规则，不是图引擎 |

## 查询合同：同一套 API 给 Loop、CLI、沙箱

Loop 跑通之后必须能问「跟这件事相关的还有什么」。沙箱里以 Issue 执行时，Agent 也要能自己查、自己确认，而不是只靠 prompt 里塞邻域。

三端共用一个 JSON 合同，只换入口：

| 调用方 | 入口 |
|---|---|
| Coordinator Loop | MCP tool `assoc_recall`（与现有 `chat_send_message` 一样挂在 `/api/mcp`，task token） |
| 沙箱 Agent | CLI `multica assoc recall`（skill 已允许 `Bash(multica *)`；镜像不必为新工具重建——若走 MCP 则 `multica mcp call` 也不改镜像） |
| 调试 / 内部 | HTTP `GET /api/assoc/recall` |

### 入参（钉钉 ID + 时间）

```text
since            必填  RFC3339 或 24h/48h
until            可选  默认 now
conversation_id  可选  钉钉 openConversationId（v1 主键）
person_id        可选  钉钉 uid，出站可以没有
issue            可选  平台 Issue identifier（MUL-123）或 --current-issue
q                可选  purpose 关键词（LIKE/bigm，时间窗内）
intent           可选
limit            默认 20，硬顶 50
```

`--current-issue` 从 `MULTICA_ISSUE_ID` 走 Issue → Task 索引。`conversation_id` / `issue` 至少一个（纯 `--q` 必须带 since，且仍限制在该 Agent）。禁止无窗全表扫。

### 出参（Agent 能直接拿去调 dws）

```json
{
  "since": "…",
  "until": "…",
  "items": [
    {
      "issue": "MUL-123",
      "purpose": "预约A与B本周五下午30分钟",
      "intent": "calendar.book",
      "status": "waiting",
      "last_touched_at": "…",
      "score": 0.91,
      "conversations": [
        { "conversation_id": "cid-a", "kind": "dm", "rel": "outreach" }
      ],
      "people": [{ "person_id": "123456", "display_name": "A" }],
      "waiting_on": [{ "conversation_id": "cid-a" }],
      "origin": { "conversation_id": "cid-origin", "rel": "spawned_from" }
    }
  ]
}
```

`purpose` 必须足够具体，LLM 精排和确认都靠它。`people` 可空。沙箱在 Issue 下：

1. 已经给哪些 **会话** 发过消息 → `conversations` / `outreach`
2. 当前 cid 的要求从哪来 → `origin` + `purpose`
3. 这件 Issue 路由到哪些 Task → 同一列表

是新事还是问旧事：**不在本层分类**，候选交给 Coordinator 提示词。

### 速度

- 覆盖索引（各文件 `CONCURRENTLY`）：
  - `assoc_task (issue_id, status, last_touched_at DESC)` —— Issue 路由到 Task
  - `assoc_task (agent_id, last_touched_at DESC) WHERE status IN ('open','waiting')`
  - `assoc_edge (agent_id, dst_type, dst_id, rel, status, last_touched_at DESC)` —— 按 cid
  - `assoc_event (agent_id, evidence_id)` UNIQUE —— 发/回去重
  - `purpose` bigm/trgm GIN（扩展可用时）
- 查询路径禁止 JOIN 整张 `event` 热表；事件明细另开 `assoc events --since` 如需要。
- 目标：单 Agent、单 cid/人、48h 窗，p99 在几毫秒到几十毫秒（本地索引点查），不在入站 ACK 路径上做关联写入。

## 消息流与绑边

```text
入站回复
    → Event(inbound, evidence_id=openMsgId) 去重
    → 不在 ACK 里写关联
    → Loop / 沙箱 assoc_recall --conversation cid --since 48h

出站发消息（优先沙箱里的单聊 send）
    → Event(outbound, evidence_id=回执msgId) 去重
    → 只绑 conversation_id；有 uid 再写人

派发新的 Issue 或挂上 Task
    → Associate：Event/Scene → Task → Issue
    → 当前已在 Issue 下则挂这个 Issue，否则新建 Issue
```

「用户是要重新弄，还是在问之前的事」→ **Coordinator 提示词**，本层不猜。

Agent 主动发消息有两条执行面，绑边必须都能接到：

### A. Coordinator / 服务端 Loop（可信）

若 Loop 最终走 Multica 控制的出站（或我们提供的 `POST /internal/assoc/bind-outbound`），在 **发送成功回执** 上写边。这是最干净的路径，应作为官方 API。

### B. 沙箱 `dws chat message send`（黄金用例现在走这里）

做简单： **发消息和回复都能识别，evidence_id 去重。** 不复活 reply tracker，不当完成事实源。

**出站**：execenv 一个薄 `dws` shim，只认 send / send-by-bot。成功回执里有 `openConversationId`（及可选 `openMsgId`）→ `bind-outbound`。没有 cid 就跳过。不绑人也可以。

**入站**：Dispatch 已有消息 id，写 `Event(inbound)`，`ON CONFLICT (evidence_id) DO NOTHING`。

同一 `openMsgId` 出站回执和入站回调撞车时，以先到为准，后到只补 `direction` 缺失字段，不插第二行。

不搞 Claude `PostToolUse`，不拿 MCP `chat_send_message` 当钉钉 cid。tool_use 扫命令行只作漏绑补救，仍不碰 completion。

Bind 幂等键：`(agent_id, conversation_id, rel)` + evidence_id。沙箱在 Issue 下查：`multica assoc recall --current-issue --since 48h`。

## Event → Issue/Task 的稳定关联（对应你的三条门）

| 门 | 实现 |
|---|---|
| 显式 ID | 审批 `关联Issue`；**派发时** `event_of` 到已有 Task/Issue |
| Scene + Active Task | 该 cid 已有 open `task_scene` / `outreach`（查询随时可读；写入跟 dispatch） |
| 语义 | v1 = 时间窗 + cid + purpose 关键词；精排 LLM |

未过门：Event.`task_id` 为空。开新 Task/Issue 还是续旧的，**Coordinator 提示词**决定。

Chat→Issue delegate 仍用 `parent_task_id`：那是 run 的父子。事边描述「为什么聊这个 cid」。

## 黄金用例逐步怎么走

1. 用户说「帮我约 A 和 B」。在当前 Issue 下开 Task，`purpose=预约A与B本周五下午30分钟`。没有 Issue 就先建 Issue。
2. 沙箱 send 给 A：只绑 **cid_A**（uid 可后补）。`Event(outbound)` + `outreach`。
3. 对 B 同样。又委托 C：再加一条边，merge props，不改表。
4. A 回复：`Event(inbound)`，`evidence_id` 去重。recall `--conversation cid_A --since 48h` 命中该 Task/Issue。
5. 派发下一轮 Issue task 时才 `event_of`。新事还是旧事由 Coordinator 看 `purpose` 列表决定。
6. `multica assoc recall --current-issue --since 48h`：A 已回、B waiting、两个 cid。

## 怎么测

   - 同一 `evidence_id` 入站+出站不双写  
   - `--current-issue` 列出两个 cid  
   - 再加一个人只是多一条边  
   - 缺 `since` → 400  
   - `--q 预约周五` 命中精确 purpose，打中「帮我看看」那种不准 purpose 应靠写入校验挡掉

3. **CLI**  
   `multica assoc recall --issue MUL-xxx --since 48h --output json` 契约测（httptest）。

4. **手工冒烟（可选，真钉钉）**

## 风险

- **群 binding key ≠ cid**：召回必须用钉钉 `openConversationId`。这条还好，按 cid 做就行。
- **多候选精排**：本层返回有序列表 + 精确 purpose；**精排交给 LLM**。
- **无 since 全表扫**：缺 since → 400。
- **purpose 太糊**：写入校验；否则 `--q` 和 LLM 都没用。
- **中文 FTS**：不要用默认 `to_tsvector` 当主路径；跟 Issue 搜索一样 bigm/trgm，窗内 LIKE 保底。
- **Person 可选**：出站不绑人时，只能靠 cid 召回。
- **PolarDB 扩展**：bigm/trgm 沿用现有 `DO $$ EXCEPTION`；embedding 列可空、v1 不建向量索引。
