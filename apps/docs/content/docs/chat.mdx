**Chat is a one-to-one conversation between you and an [agent](/agents)** — stepping outside the [issue](/issues) board. The agent sees no issues and cannot change any issue, and the entire conversation is **fully private** (nobody else in the [workspace](/workspaces), including admins, can see it). It fits discussing an approach with an agent, brainstorming, or asking a question that does not belong to any issue.

## Why not just @-mention the agent?

[@-mention](/mentioning-agents) **pulls the agent into** an issue's context — it reads the issue description and every historical comment, and it can change the issue. Chat flips this: **it pulls you out of** the issue — the agent only sees this single conversation, has no awareness of any issue, and has no entry point to modify one.

Two rules of thumb:

- You want feedback grounded in the context of a specific issue → [@-mention](/mentioning-agents)
- You want to discuss a topic unrelated to any issue (or you do not want anyone else to see the discussion) → Chat

## Start a conversation

Open **Chat** from the sidebar, pick an agent, and start a new conversation. The interface feels like any messaging app: you send a message, the agent replies. Messages waiting in the same Session are collected into one queued run; once that run starts, later messages form the next queued run.

### Manage Chat Sessions from the CLI

The CLI talks directly to the Chat Session API; these commands do not create or depend on an issue.

```bash
multica chat list
multica chat start --agent Lambda --title "Release review" "Review today's release"
multica chat send abcd "Also check the rollback plan"
multica chat messages abcd
multica chat get abcd
```

`abcd` can be any unique Session ID prefix of at least four characters. Use `-` as the message to read multiline content from stdin:

```bash
cat prompt.md | multica chat send abcd -
```

`chat start` and `chat send` return JSON containing `session_id`, `message_id`, `task_id`, and `collected`. A `collected: true` result means the message joined the existing queued execution for that Session.

### Reliable Turn replies from a sandbox

Automation can bind a stable `session_key` and a sandbox-local final reply template to a Session. The key makes create/resume idempotent; every returned `task_id` is the Turn ID and remains queryable after reconnects.

Install the bundled DWS post-processor in the sandbox:

```bash
multica chat reply-template install dws-reply \
  --script ./scripts/chat-reply-templates/dws-reply.sh
```

Create or resume a Session with a fixed DWS reply target:

```bash
cat > reply-config.json <<'JSON'
{
  "mode": "reply",
  "openConversationId": "cid...",
  "openMessageId": "msg...",
  "senderOpenDingTalkId": "user...",
  "aiTag": true
}
JSON

multica chat start \
  --agent Lambda \
  --session-key "dingtalk:cid...:thread" \
  --reply-template dws-reply \
  --reply-config reply-config.json \
  "Answer this message"
```

A Session with a reply template waits for its Turn automatically. The CLI ignores intermediate streaming messages, polls the durable Turn endpoint until `completed`, `failed`, or `cancelled`, then passes the final Turn JSON to the installed script on stdin. The script runs inside the caller's sandbox and uses that sandbox's DWS login; Multica Server never uploads or executes it.

You can send and recover state independently:

```bash
multica chat send --session-key "dingtalk:cid...:thread" "Follow-up"
multica chat turn <session-id> <task-id> --wait --deliver
```

The Turn response separates agent execution (`status`, `reply`) from post-processing (`reply_delivery_status`, `reply_delivery_error`). WebSocket events may make UI updates faster, but the persisted Turn query is the reliability source and survives a dropped stream or restarted caller.

The bundled DWS script passes the immutable Turn ID as DWS `--uuid`, so retrying delivery after a sandbox crash is idempotent within DWS's 24-hour deduplication window.

### Token-authenticated API smoke test

The repository includes a standard-library-only Python smoke test for the durable Session/Turn API. Pass secrets through environment variables so the Token does not appear in shell history:

```bash
export MULTICA_SERVER_URL="https://your-multica.example.com"
export MULTICA_TOKEN="mul_..."
export MULTICA_AGENT_ID="agent-uuid"
# Optional when the Token is not already bound to one workspace:
export MULTICA_WORKSPACE_ID="workspace-uuid"

python3 scripts/chat_api_smoke.py \
  --session-key "smoke:chat-reply:$(date +%s)" \
  --message "Reply with API_SMOKE_OK" \
  --expect-reply-contains API_SMOKE_OK
```

To verify the reply-template snapshot without running DWS from the Python process, add `--reply-template dws-reply --reply-config @reply-config.json`. The resulting Turn should remain `reply_delivery_status: pending` until the initiating sandbox executes its installed template.

## What an agent can and cannot do in chat

Agents run in a **fully sandboxed** mode inside a conversation.

**Can do:**

- Answer the questions in your current message
- Use its configured [skills](/skills) and MCP
- Read and write files in its own working directory
- Call `multica` CLI commands that do not need issue context (for example, querying basic workspace info)

**Cannot do:**

- **See any issue** — the prompt the agent receives has no issue IDs, and commands like `multica issue list` return empty
- **Change any issue** — without issue context, API calls are blocked by permission checks
- **See other conversations** — conversations are fully isolated
- **@-mention anyone or any agent** — chat is a private space with no path to notify others

## How multi-turn context is preserved

Chat maintains multi-turn context via **provider session resumption** — the agent establishes a provider session on its first reply (for example, a Claude session), and the session ID is stored. On the next message, the task dispatch passes that ID back so the agent **resumes from where it left off** without re-reading history every time.

If **one turn fails**, Multica looks up the previous task that had established a session ID (whether that task succeeded or failed) and tries to resume — a single failure in the middle does not drop the memory of the whole conversation.

Note: not every provider actually implements session resumption — see the [**Providers Matrix**](/providers) for support status.

## Archive a conversation

Conversations you no longer want to see can be archived — right-click in the conversation list or use the "Archive" button on the detail page. After archiving:

- The conversation disappears from the active list (you can still find it in the "Archived" view)
- Historical messages, session ID, and the working directory are all preserved — nothing is deleted

<Callout type="warning">
**There is no "restore" button after archiving.** There is currently no entry point to move an archived conversation back to active. If you want to continue the thread later, you will need to start a new conversation. To revisit content in an archived conversation, open the "Archived" view and read through the history.
</Callout>
