# Roles for Tag evaluation

Who plays whom in the EmployeeLoop / Tag evals.
- Machine-readable sources: `registry.json` (harness actor keys, profiles, observer-relative ids, conversations) and `cases/v2/world.json` (story names and roles, generated by `cases/v2/_build`).
- Keep all three consistent. Change `_build/render.py` + `_build/common.py`, run `python3 cases/v2/_build/build.py`, then update `registry.json`.
- Identifiers below are ids, not secrets. Tokens live in the macOS keychain and are never written anywhere.

Columns:
- **Harness key**: the `registry.json` actor key, which case `roles` map to.
- **dws-env selector**: what `dws_env.py as <selector>` accepts.
- **Corp**: the DingTalk organisation the account acts in.
- **Allowed** / **Limits**: what the account can and cannot do as a test participant.

Limits, measured 2026-10-03, which the harness enforces:

- **No @.** A DEAP actor cannot @ anyone. Its plain group lines are never delivered to the employee (native delivery is @-only).
- **Quote-reply arrives as an @.** Quote-replying any employee message renders as `@Qwen-Real …` and arrives as a native @ event. This is the only way a DEAP actor can address the employee.
- **No DM.** DE↔DE 1:1 chats do not work, and the employee is a DE. An unconnected actor that receives a DM auto-replies a fixed template.
- **Auto intro cards.** Joining a group auto-posts an intro card and a 「暂无可展示的最终产物」 placeholder. The grader filters both.
- **Never connect or modify an actor.** Log in with `dws_env.py as 'Real Niubility/DingTalk-FDE Director' -- dingtalk-tag manage login --agent-uuid <uuid>`, then run `e2e.py gw prepare`.
- **Lease per case.** The driver leases an actor on the DWH board before using it (prod issue `5598799a-eedb-42a3-be05-8510fccfa180`, profile `fde-prod`, key `act_<uuid>`) and releases it afterwards.
- **Read-back by a human.** Every DEAP send is read back by a human reader of the conversation, matched by sender id.
